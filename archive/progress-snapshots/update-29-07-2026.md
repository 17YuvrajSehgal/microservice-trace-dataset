# StrataTrace — Progress Update (29 July 2026)

Prepared for supervisor discussion. Summarizes the work completed to date on
the four-modality observability dataset and the per-task modality-ablation
study targeting **MSR 2027** (Data & Tool Showcase, abstract Nov 5 / paper
Nov 10; a coupled technical-track study paper).

---

## 1. What StrataTrace is

A reproducible **four-modality incident dataset** collected from the Sock Shop
microservice benchmark under labeled fault injections:

- **Metrics** (Prometheus: per-service + per-container via cAdvisor + host)
- **Logs** (per-container, timestamped)
- **Distributed traces** (native OpenTelemetry spans)
- **Kernel traces** (LTTng — the differentiator; no existing microservice
  incident dataset includes a kernel layer)

Plus a planned study measuring **how informative each modality is for each
operations-reasoning task** (RCA, anomaly detection, incident explanation,
repair), including cost–benefit — the research questions from your guidance.

**Positioning (verified against July-2026 literature):** the closest datasets
(RCAEval, LEMMA-RCA, OpenRCA) stop at metrics/logs/traces — none has a kernel
layer. Agent-observability tools (AgentSight) and agent-failure datasets
(TRAIL, Who&When) are separate and reserve the agentic follow-up paper.

## 2. Headline: the dataset now exists

**A complete v1 dataset has been collected: 40 runs, 164 GB, all four
modalities time-aligned, all faults verified.**

| | Count | Verification |
|---|---|---|
| Fault runs | 34 | **31 confirmed + 3 borderline** |
| Normal (reference) runs | 6 | baselines (steady + burst) |

- **Zero genuine collection failures.** Every fault behaved exactly as
  pre-registered.
- The 3 "borderline" runs are all `dependency_outage` — the one fault that is
  *metrics-weak by design* (see §5), so borderline is the honest, expected
  verdict, not a defect.
- Cross-modality clock alignment measured at **~0.001–0.003 ms drift** per run.

## 3. What was accomplished (three phases, ~one week)

**Phase 0 — the alignment gate (PASSED).** Proved that a single request can be
traced across all four modalities on one clock: on a real run, the audit tool
followed one `POST /orders` request through its distributed-trace span tree,
correlated log lines, load-generator record, metric window, and **2.3 M kernel
events** attributed to processes by PID/TID — all time-aligned. This is the
core technical claim of the whole dataset, now empirically demonstrated.

**Phase 1 — fault catalog + calibration.** Built and calibrated a two-axis
fault catalog (host-wide vs service-targeted × resource vs application):
slow database, error storm, service CPU/memory caps, dependency outage, queue
backlog, noisy neighbor, host CPU saturation. Each fault:
- injects and cleans up reproducibly, emitting machine-readable ground truth;
- declares, *before any experiment*, which modality should be most informative
  (pre-registered in `fault_catalog.md`);
- is verified automatically — a QC tool checks the fault actually moved its
  declared target metric and writes a confirmed/borderline/unconfirmed verdict.

**Phase 2 — the collection campaign (COMPLETE).** A one-command driver ran the
~40-run matrix (faults × intensities × workloads × repeats) unattended, with
per-run QC. Result in §2.

Instrumentation added along the way: the Sock Shop front-end (Node) and
catalogue (Go) services were forked and instrumented for native OpenTelemetry
so distributed traces cover the full request path, not just the four Java
services that were traceable before.

## 4. Key methodological decisions (for discussion)

- **Scale: ~40 runs, not a benchmark.** An earlier draft over-scoped to
  150–200 runs (~2–4 TB). We deliberately reduced to a tight, diverse,
  purpose-built set — fault *diversity* over repeats — which answers every
  research question at a size comparable to peer datasets (OpenRCA 68 GB) and
  is easy for others to use. **This is a point I'd like your view on.**

- **Kernel event profile: curated, memory excluded** (per your advice). Rather
  than capture all kernel tracepoints (~8 GB/run, expensive), we capture
  syscalls + scheduler + block-I/O + network + IRQ, and **exclude memory
  events** (the highest-volume class). This is what the wait-attribution
  analysis actually uses, and it cut per-run kernel size ~3×. The same profile
  is used for every run for consistency; memory instrumentation can be added
  later if the analysis needs it.

- **Pre-registration.** The fault→modality predictions were committed to the
  repository (git-timestamped) *before* collection, with frozen scoring rules
  and explicitly-stated rival hypotheses. Now that the campaign is collected,
  these predictions are effectively frozen — any change goes through a dated
  amendment log. This turns the study from description into hypothesis testing.

- **Kernel "representation ladder" (planned).** Raw kernel traces are unusable
  by LLMs, so the dataset will ship each run's kernel data at four levels: raw
  CTF → per-service kernel KPIs → per-request wait attribution → templated
  natural-language digests. "How to present kernel data to an LLM" is itself an
  open sub-question.

## 5. Findings already emerging (research-relevant)

Two results from calibration/collection directly support the dataset's core
thesis — *that kernel traces see things the other modalities cannot*:

1. **A frozen dependency is invisible to metrics and logs.** When `payment` is
   paused, its callers' HTTP requests *hang* on a blocked socket read rather
   than failing — so no error status is ever logged or counted. The metrics
   verdict is legitimately weak (borderline), while the kernel trace shows the
   caller's threads blocked in `read()` on the payment socket. A concrete
   instance of "kernel wins."

2. **CPU contention is host/kernel-visible but application-blind.** The
   noisy-neighbor fault consumes ~0.75 core while service latency stays within
   normal variance (+6% carts, 0% catalogue) — i.e. app-level modalities are
   near-blind by construction, while the contention is plain in scheduler
   events. The premise held empirically.

These are exactly the kinds of cases the ablation study is designed to
quantify.

## 6. Engineering robustness (why this is reproducible)

- One-command VM bootstrap + collection driver; a troubleshooting doc capturing
  every hard-won fix; the deployment pinned as a git submodule of our fork so
  each run cites the exact code it was collected against.
- A genuine bug was caught *during* the campaign (the verification tool
  mishandled sparse-baseline NaN values, mislabeling a fault that had actually
  fired). It was fixed live, the affected runs re-verified, and collection was
  never affected — only a verdict. This is the kind of QC the pre-registration
  discipline surfaces.
- The collection VM ran out of cloud capacity in its zone mid-effort; it was
  snapshotted and rebuilt in a sibling zone with no data loss. Noted only to
  show the pipeline survives real operational hiccups.

## 7. Current state & what's next (Phase 3)

The dataset is collected and stored (VM stopped to save cost; data persists).
Remaining work:

1. **Package the release** — compress and build two tiers: a small **Lite**
   tier (kernel KPIs/digests + app modalities, ~20–30 GB, Zenodo DOI) and a
   **Full** tier (+ raw curated kernel, ~120 GB). Add a datasheet + loader SDK.
2. **Build the kernel representation ladder** (L1–L3 derivers) against the 40
   real runs.
3. **Run the modality-ablation study** — the four tasks × modality subsets over
   the 40 runs, with LLM evaluators and classical baselines, budget-matched so
   the comparison measures information, not token count. This is the study
   paper's empirical core (RQ1–RQ6).

Timeline: Phases 0–2 finished in the first days, well ahead of the Nov 5
abstract deadline; Phase 3 (derivers + study + writing) is the bulk of the
remaining runway.
