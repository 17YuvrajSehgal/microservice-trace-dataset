1 · Why an index

babeltrace2 cannot seek

To read one second of trace it decodes from the beginning and throws the rest away. So a query costs what its depth costs — not what it returns.

what you ask fortime it takes
1 second, 3 s into the trace9.6 s
1 second, 213 s into the trace133 s

Same amount of data returned. Fourteen times the cost.

1 · Why an index

So we decode once, and never again

A dozen questions the naive way would cost ten minutes and still show only slivers of the recording. One full pass costs about what a single deep query costs — and then answers everything.

133 sone deep query, before
~2 sany full-trace question, after

This is what makes the whole thing viable. Without it the agent is guessing from fragments.

2 · What the index holds

One row per 100 ms, per event, per process, per container

bucket_start_s   event   procname   pid_ns   count   value_sum
pid_ns — which container The only thing in a kernel trace that tells java in one container from java in another. Without it you can see a fault but never say whose it is.
value_sum — quantity, not count In one trace the guilty workload ranked 8th by event count but 1st by CPU time. Counting alone would have missed it.
3 · The toolbox

Ten read-only tools

ctf_timespanWhen does this recording start and end?
ctf_timelineCount one event across the whole recording — the change-point finder
query_ctfCounts and busiest processes in a window I choose
ctf_procdiffWhat differs between window A and window B

run_pythonWrite and run its own analysis code, sandboxed
blueprint_toolRun the blueprint's own scripts, with its exact commands
note_findingWrite a finding down — only these reach the answer
submit_diagnosisCommit to the verdict

The first five read the index and answer in seconds. ctf_lines is the only one that touches the raw trace, so it is deliberately restricted.

4 · The blueprint

A blueprint is a folder, not a prompt

4_svc_mem_cap/
  README_v1.md    the method: what the fault is, how to tell it from
                  its look-alikes, and the steps in order
  tools/          the scripts that method tells you to run

Handing one to the agent does two things at once:

  1. The method text becomes part of its instructions — including a look-alike table.
  2. The blueprint's own scripts become a callable tool, so it runs those commands rather than improvising.
4 · The blueprint

What a blueprint actually encodes

mm_vmscan_memcg_reclaim means this container's own limit is biting.

A host-wide memory shortage uses different events — direct_reclaim, and the kswapd thread.

The event name alone separates "this container's cap" from "the machine is full."

That is the kind of distinction that makes a verdict defensible to an engineer — and it is measured on our own data before it goes in the blueprint, never asserted from the model's general knowledge.

The synthesiser has no tools It cannot go and look at anything. It can only weigh evidence the workers recorded — so the final answer cannot be improvised.
Only written findings survive Anything a worker saw but did not write down is lost. Harsh — but it forces evidence to be stated rather than implied.
6 · Stopping

When does it stop?

  1. A worker stops when it decides it has nothing left to ask — or it hits its turn limit.
  2. A worker that recorded nothing gets one nudge: silence looks identical to "checked and found nothing", so we make it say which.
  3. The reviewer may order one extra round. Never more than two.
  4. The synthesiser commits: what, where, when, evidence, confidence.

Cost is bounded throughout — every tool reply is capped, and old output in a long conversation is stubbed out so cost does not grow with the square of the turns.

7 · The method

How it narrows down — the human workflow

  1. Orient. How long is this recording?
  2. Scan. Count an event across the entire recording. A step up or a collapse is a candidate.
  3. Doubt it. Confirm against a second, unrelated event — a step in everything means the workload changed, not that something broke.
  4. Compare. Pick a suspect window and a quiet window; diff them per container.
  5. Attribute. Which pid_ns moved? That is the container.
  6. Confirm. Pull a handful of raw event lines and read the mechanism directly.
  7. Commit. Name what, where and when — with the numbers.
The output

What a finished answer looks like

Verdict: ttmem — memory limit — 04:31:09–04:31:37 — confidence 0.87

Evidence: 8,937 cgroup-reclaim events and 18,132 block reads (4.76 GB) in the active window, against zero reclaim in the quiet window.

Every number there can be checked independently, against the trace and against the cgroup counters. That is the bar — not a plausible sentence, a claim an engineer can falsify.
