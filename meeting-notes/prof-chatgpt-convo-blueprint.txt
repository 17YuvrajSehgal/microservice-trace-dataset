Here are three more concrete examples. The key separation is:

Intent layer: states the diagnostic or operational goal.
Blueprint layer: defines the reusable, declarative procedure for achieving that goal.
Runtime binding: selects the available tools that can provide each required capability.
Example 1: Intermittent Checkout Failures
Problem

A checkout service occasionally returns an error, but the problem cannot be reproduced consistently.

Intent

Diagnose intermittent checkout failures during the last two hours.

The intent may also include constraints:

Target: checkout-service
Time window: last 2 hours
Priority: minimize production overhead
Expected output: ranked root causes with supporting evidence
Matched Blueprint

Intermittent Transaction Failure Blueprint

The blueprint could define:

required_data:
  - distributed request traces
  - application error logs
  - database query events
  - deployment and configuration changes
  - network timeout metrics

analysis_steps:
  - separate successful and failed transactions
  - compare their execution paths
  - identify the first point of divergence
  - correlate failures with database, network, and deployment events
  - rank candidate causes based on consistency and temporal proximity

adaptive_actions:
  - increase tracing for requests matching the failure signature
  - collect database details if failures converge on one query
  - collect network telemetry if timeout patterns are detected

outputs:
  - ranked root-cause candidates
  - failed-request timeline
  - supporting traces and logs
  - recommended next diagnostic action
Possible Tool Binding

The blueprint does not name these tools directly. The runtime may bind its capabilities to:

OpenTelemetry for distributed traces
Prometheus for metrics
Loki or Elasticsearch for logs
Kubernetes events for deployment changes
Trace Compass for timeline and correlation analysis
An internal company tool for failure classification

The same blueprint could work in another company with a different observability stack.

Possible parameters:

Matched Blueprint

CPU and Scheduler Bottleneck Diagnosis Blueprint

required_data:
  - application request spans
  - thread execution events
  - thread scheduling events
  - context switches
  - CPU frequency and utilization

  - lock and blocking events

derived_information:
  - on-CPU time

  - thread migration frequency
  - per-request execution delay

analysis_steps:
  - correlate request latency with thread execution
  - identify periods of high scheduler waiting
  - detect lock contention and blocked threads
  - distinguish CPU saturation from application-level blocking
  - identify affected processes, threads, and requests

outputs:

  - critical execution interval
  - responsible process or thread

Example 3: Adaptive Telemetry Collection Under an Overhead Budget
Problem

The company wants enough telemetry to diagnose latency problems, but continuous detailed tracing is too expensive.

Intent

Maintain sufficient diagnostic evidence for latency incidents while keeping telemetry overhead below 3%.

This intent differs from a simple diagnosis request. It defines a continuous observability objective.

Matched Blueprint

Cost-Bounded Adaptive Observability Blueprint

objective:
  preserve latency diagnosability under a fixed overhead budget

baseline_collection:
  - service-level latency metrics
  - error rate
  - request volume
  - lightweight sampled traces

escalation_triggers:
  - p99 latency exceeds threshold
  - error rate increases
  - latency pattern becomes unstable
  - anomaly confidence exceeds configured value

escalation_stages:
  stage_1:
    collect:
      - additional distributed traces
      - service dependency metrics

  stage_2:
    collect:
      - host metrics
      - process-level events
      - network telemetry

  stage_3:
    collect:
      - kernel scheduling traces
      - detailed request-aware traces
      - selected stack or profiling information

control_rules:
  - estimate collection overhead before escalation
  - select the highest-value evidence within the available budget
  - stop detailed collection when sufficient evidence is obtained
  - return to baseline after the incident window

outputs:
  - collected evidence package
  - estimated telemetry cost
  - diagnostic coverage
  - escalation history
  - reason for each collection decision
Possible Tool Binding

Depending on the environment, the runtime could use:

Prometheus or an internal monitoring system for baseline detection
OpenTelemetry sampling controls for request tracing
LTTng, eBPF, or a proprietary collector for deeper tracing
Babeltrace for conversion into a common event representation
Trace Compass or an automated analysis engine for diagnosis
Agentic Role

This is a strong agentic use case. An agent can:

Observe that baseline data is insufficient.
inspect the blueprint’s permitted escalation actions.
select additional capabilities within the overhead limit.
evaluate the new evidence.
stop collection when it reaches a diagnostic conclusion.

The agent does not invent an unrestricted procedure. It operates within the blueprint’s capabilities, policies, budgets, and safety constraints.

Example 4: GPU Inference Slowdown
Problem

An AI inference service becomes slower, but GPU utilization appears normal.

Intent

Determine why the inference latency of Model X increased from 80 ms to 250 ms.

Matched Blueprint

AI Inference Latency Diagnosis Blueprint

required_data:
  - request arrival and completion timestamps
  - model-server queueing events
  - host preprocessing time
  - CPU-to-GPU transfer time
  - GPU kernel execution time
  - GPU memory utilization
  - batching decisions
  - co-tenant activity

  - identified bottleneck stage
  - affected requests
  - evidence timeline
  - recommended mitigation

This blueprint could bind to OpenTelemetry, NVIDIA DCGM, CUPTI, kernel tracing tools, or proprietary GPU telemetry systems.

A Useful Design Rule

The blueprint should describe a capability such as:

Collect kernel scheduling events for the affected process.

It should avoid directly stating:

Run LTTng with this exact command.

The first form is tool-agnostic. At runtime, a capability resolver can select LTTng, eBPF, perf, or another available provider.

A practical end-to-end flow would therefore be:

Problem
   ↓
Intent
   ↓
Intent Resolver
   ↓
Selected Observability Blueprint
   ↓
Capability and Policy Resolution
   ↓
Tool-Specific Execution Plan
   ↓
Data Collection and Analysis
   ↓
Evidence, Diagnosis, and Recommended Action

The blueprint is therefore closer to a reusable package of observability knowledge, execution logic, adaptation rules, and output contracts than a traditional static workflow.

Capability binding and capability registry

Tools primarily generate or process evidence. The runtime and diagnostic components interpret that evidence. Evidence may trigger another collection or analysis step before the final diagnosis.

Tools → Evidence → Processing/Analysis → Findings/Diagnosis

  + Historical Effectiveness
  - Expected Cost
  - Policy Risk

For the throughput example, the system might rank:

1. CPU and Scheduler Bottleneck Diagnosis Blueprint    0.91
2. Application Blocking Diagnosis Blueprint            0.83
3. General Service Latency Diagnosis Blueprint         0.69
4. Network Congestion Diagnosis Blueprint               0.31

The runtime could select the first blueprint or compose the first two if the intent explicitly asks to distinguish scheduler delay from application blocking.

The selected blueprint is generic. The runtime creates an instance for the current incident.

This stage can be fully automatic when the normalized intent and infrastructure inventory provide sufficient information.

4. Automatic capability resolution

The blueprint asks for abstract capabilities rather than named tools.

For example:

required_capabilities:
  - collect_kernel_scheduling_events
  - collect_request_spans
  - reconstruct_thread_states
  - correlate_requests_with_threads
  - classify_scheduler_bottlenecks

The runtime queries a Capability Registry:

providers:

  - provider: LTTng
    capabilities:
      - collect_kernel_scheduling_events
      - collect_user_space_events
    platform: linux
    estimated_overhead: 2-5%

  - provider: eBPF Collector
    capabilities:
      - collect_kernel_scheduling_events
      - collect_process_metrics
    platform: linux
    estimated_overhead: 1-3%

  - provider: OpenTelemetry
    capabilities:
      - collect_request_spans
      - propagate_request_context

  - provider: Trace Compass
    capabilities:
      - reconstruct_thread_states
      - analyze_scheduling_delays
      - generate_execution_timelines

  - provider: Internal Correlation Engine
    capabilities:
      - correlate_requests_with_threads
      - classify_scheduler_bottlenecks

The runtime can then automatically determine which combination satisfies the blueprint.

5. Automatic tool binding

Suppose both LTTng and eBPF can collect scheduling events.

The binder may select between them according to:

expected overhead;
operating-system support;
permissions;
data fidelity;
availability;
collection duration;
privacy policy;
compatibility with downstream analysis;
current system load.

For example:

Required capability:
Collect kernel scheduling events

Available providers:
LTTng: high fidelity, estimated overhead 4%
eBPF: medium-high fidelity, estimated overhead 2%

Constraint:
Total overhead must remain below 5%

Decision:
Select eBPF for initial collection.
Escalate to LTTng only if eBPF evidence is insufficient.

This is an automated policy-aware binding decision.

7. Automatic adaptive replanning

The first execution plan may not collect enough evidence. The runtime can assess evidence sufficiency.

Example:

Initial finding:
High off-CPU time was detected.

Uncertainty:
The system cannot distinguish lock waiting from I/O waiting.

Current confidence:
0.54

Required additional capability:
Collect lock acquisition and blocking events.

The adaptive planner can then:

identify the unresolved question;
inspect permitted actions in the blueprint;
select an additional capability;
bind it to an available provider;
estimate the added overhead;
execute the additional step;
update the diagnosis.

Example:

Evidence insufficient
        ↓
Request lock-wait evidence
        ↓
Bind capability to user-space tracing provider
        ↓
Collect targeted lock events for 60 seconds
        ↓
Reanalyze
        ↓
Confidence increases from 0.54 to 0.88

This is where an AI agent can add substantial value. However, its actions should remain constrained by the blueprint and policy engine.

What should remain controlled

Automation should not mean unrestricted agent access to production systems.

The runtime should require human approval or stricter policy validation for actions such as:

enabling high-overhead tracing;
restarting services;
changing production configuration;
collecting sensitive payloads;
accessing protected hosts;
retaining personally identifiable information;
executing remediation actions;
collecting full memory dumps;
extending collection beyond the approved time or cost budget.

A policy can express this explicitly:

approval_rules:

  automatic:
    - query_existing_telemetry
    - enable_collection_below_3_percent_overhead
    - run_read_only_analysis

  requires_approval:
    - collection_above_3_percent_overhead
    - memory_dump_collection
    - production_configuration_change
    - service_restart
    - automatic_remediation

Therefore, the architecture can support different autonomy levels.

Suggested autonomy levels
Level 0: Manual

A human selects the blueprint, tools, and execution steps.

Level 1: Assisted

The system recommends candidate blueprints and providers, but a human confirms them.

Level 2: Policy-controlled automation

The system automatically selects and executes low-risk plans within defined constraints.

Level 3: Adaptive diagnosis

The system collects additional evidence and modifies the plan automatically within the blueprint’s allowed action space.

Level 4: Closed-loop remediation

The system diagnoses and applies corrective actions automatically, subject to strict policies and rollback mechanisms.

For the first implementation and patent description, Level 2 and Level 3 are the most credible targets. Closed-loop remediation adds substantial safety and validation requirements.

Role of AI

AI can support several stages:

Intent extraction
Blueprint retrieval and ranking
Blueprint composition
Execution-plan generation
Evidence interpretation
Adaptive replanning
Natural-language diagnosis

However, deterministic components should validate AI output:

AI proposal
   ↓
Schema validation
   ↓
Capability validation
   ↓
Policy validation
   ↓
Cost and overhead validation
   ↓
Execution

A robust architecture would therefore use:

AI-assisted planning with deterministic validation and policy-controlled execution

rather than allowing an AI agent to call arbitrary tools directly.

Role of MCP

MCP can help an agent discover and invoke capabilities such as:

query OpenTelemetry traces
start an LTTng session
run a Trace Compass analysis
retrieve a generated report

However, MCP does not itself provide:

blueprint selection;
policy resolution;
provider ranking;
overhead optimization;
evidence sufficiency assessment;
adaptive planning;
blueprint lifecycle management.

MCP can act as one adapter layer between the runtime and tools:

Runtime
   ↓
Capability Binding
   ↓
MCP Adapter, REST Adapter, CLI Adapter, or Native API Adapter
   ↓
Concrete Tool

Therefore, MCP is useful, but it should remain replaceable.

The strongest design is therefore not simply:

Agent chooses a tool.

It is:

The system automatically interprets an intent, selects or composes a reusable observability blueprint, resolves its abstract capabilities under environmental and policy constraints, generates a concrete execution plan, evaluates the resulting evidence, and adaptively revises the plan until a diagnosis or stopping condition is reached.
