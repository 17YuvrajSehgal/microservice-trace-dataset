## What we did, step by step

### 1. Made the analysis three times faster (task A3)

Reading one kernel trace took about 23 minutes because seven separate analysis scripts each read
the same file. Now the file is read once and shared: **about 7 minutes**.

While doing this we found our results **were not reproducible** — running the same analysis twice
could give different output, because of unstable sorting. Fixed and verified.

### 2. Listed the reasons a request gets slow (task A1)

Eleven single causes plus five combinations. The important column is not the list — it is
**"can kernel traces actually see this?"**, answered from our own recorded data rather than from
textbooks.

Result: 6 yes, 1 partly, 1 works on one application only, 2 proved impossible, 1 untested.

We also checked one thing directly on the machine: **kernel-level lock contention cannot be
recorded** on standard Ubuntu. So the lock work is about application-level locks, and we say so.
That closes the question you raised, with a negative answer.

### 3. Built 15 new fault types (task B2)

Ten new fault injections plus five deliberately-introduced code bugs. All tested end to end.

They include the two cases you liked most: **priority inversion** and **Nagle / delayed-ACK**.
Both are cases where nothing looks busy and an AI agent alone is unlikely to guess the cause.

Getting these right was most of the work. Several "working" faults turned out to be doing
nothing:

- One fault claimed to hold 400 database connections. The database said it had **3**. The check
  had been reading our own program's claim instead of asking the database.
- One fault's mechanism could never have worked — it was limiting the wrong process.
- One network fault was almost inert because the rule sat in the wrong place in the network stack.

Each was found by measuring the effect rather than trusting the script's own report.

### 4. Collected the v2 dataset

Two new cloud machines, one per application, in the same region — the old setup had them in
different regions, which meant we could never tell an application difference from a machine
difference.

| | v1 | v2 |
|---|---|---|
| runs | 109 | **303** |
| applications | 2 | 2 |
| fault types | 13 | **28** |
| repeats per fault | 3–7 | 5–11 |
| size | 148 GB | **1.18 TB** |

All four data types (kernel traces, metrics, logs, request traces) in every run. 302 of 303
kernel traces have no data loss at all.

### 5. Moved everything to the university cluster and shut down the cloud

The full dataset is now on Trillium, verified run-by-run (303 of 303). We then **deleted the
cloud machines**, which were costing about $120/month.

We also extracted a working copy: 303 runs, fully uncompressed, 7.3 TB, ready to analyse.

### 6. Tested all seven blueprints against the new data

This is the first honest measurement of the library — previously each blueprint had been checked
on roughly one run per fault.

**Overall 50% → 76%.** False alarms stayed at 3 out of 826 opportunities — the library is very

Two blueprints we deliberately did **not** touch. Train Ticket has no confirmed runs for those

## The two findings worth discussing

### Finding 1: numbers measured on one system do not transfer

Before the fix, the library scored **71% on Sock Shop and 29% on Train Ticket**. Every threshold
inside it had been measured on Sock Shop.

The clearest example: one rule required host CPU to be above 55%. On Train Ticket the healthy
runs sit at 66–71% and the faulty runs at 21–28% — **the order is reversed**. That rule would
call every healthy run faulty and every faulty run healthy.

### Finding 2: but not all numbers are equally fragile — and this is the sharper claim

One threshold survived both applications perfectly: "host CPU above 95%".

The difference is *what the number is attached to*.

- **55% is a system's normal level.** It differs per machine. Ours even drifted during collection.
- **95% is next to a physical limit.** CPU usage cannot exceed 100%, so "almost out of CPU" means
  the same thing on any machine.

So the claim is not "thresholds are bad". It is:

> **A number tied to a physical limit transfers between systems. A number tied to a system's
> normal level does not.**

That is testable, and we have measured it on two applications.

---

## A result that supports the thesis of the dataset

On one fault on Train Ticket, the **kernel-trace blueprint found the fault in all 8 runs, while
the metrics-based check could only confirm 4 of 8.**

Those 4 are runs where the metrics are blind *by construction* — the fault adds network delay, and
that application publishes no latency metric, so there is nothing for metrics to see. The kernel
trace sees it anyway.

That is exactly the argument for collecting below the application layer.

---

## We also tested "blueprints without fixed numbers"

A concern we wanted to answer with data: should a blueprint contain hard-coded numbers at all, or
should it give the agent a hint and let the agent judge?

We built a version that uses no fixed numbers. Instead it compares each run against **that
system's own healthy runs**, and each blueprint says only which direction a signal should move.

| | with fixed numbers | without |
|---|---|---|
| correct diagnoses | 76% | 71% |
| false alarms | 0.4% | 4.6% |
| runs with an ambiguous answer | 3 | **0** |
| system-specific numbers needed | 12 | **1** |

**As a replacement it is worse.** As a *hint layer for an agent* it is better at that job — it
always narrows to one candidate, and it needs one number instead of twelve, so it moves to a new
system without re-measuring anything.

Conclusion: keep both. The fixed-number rules are the deterministic baseline the study already
promises; the number-free version is what the agent should be handed.

**Honest note:** getting the number-free version right took five attempts, and each failure was
subtle. The fixed-number rules are wrong in ways you can see. The number-free version is wrong in
ways that needed 136 labelled runs to detect. That is worth saying in the paper.

## Problems we found and recorded rather than hid

- **103 Train Ticket runs lost their client-side request log.** A bug in the load generator: it
  only wrote the file after every worker finished, and under a fault a worker never finishes. The
  other three data types are complete. Fixed, but those files cannot be recovered.
- **Baseline machine load drifted during collection** — 4.6× on one application. It means any
  measurement based on an absolute level partly measures *when* a run happened. Comparisons
  within a run are unaffected.
- **One fault does not actually happen on Train Ticket.** The CPU cap has 60× more headroom than
  it needs, so it never binds. Recorded, not papered over.

In plain words, each one answers a different question:

- host CPU saturation - the whole machine ran out of CPU
- CPU contention - another program stole some CPU
- service CPU throttle - one service hit its own CPU limit
- host disk saturation - something is flooding the disk
- service memory cap - one container hit its memory limit
- network path degradation - the network is dropping packets
- slow database - a service is stuck waiting on the database
