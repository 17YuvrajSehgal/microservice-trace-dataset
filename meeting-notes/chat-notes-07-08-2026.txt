How Much Observability Can We Lose Before Diagnosis Breaks?
How robust are software diagnosis techniques to realistic telemetry degradation, and what telemetry must be preserved to retain diagnostic capability?

RQ1 — How does telemetry degradation affect diagnosis?
Systematically reduce sampling rate, temporal resolution, and service coverage.
Measure AD and RCA degradation.
You might discover nonlinear thresholds.
For example:
100% traces → 25% traces:

almost no difference.
25% → 5%:

RCA collapses.
That's much more actionable than simply saying traces are useful.

RQ2 — Which faults are resilient to degraded observability?
Your fault catalog is perfect for this.
You have CPU, disk, memory, network, DB latency, error storms, CPU throttling, memory limits, dependency outages, queue backlog, noisy neighbor, and service-network faults.
You can construct something like a:
Fault × Observability-Degradation Map
Maybe:
CPU saturation survives metric downsampling.
Error storm survives trace loss because logs scream.
Slow DB survives trace sampling but not kernel removal.
Dependency outage becomes extremely difficult once the affected service is uninstrumented.
That becomes a useful empirical contribution.

RQ3 — Can one telemetry layer compensate for another being missing?
Imagine removing traces from the faulty service.
Compare:
Metrics + logs + traces
versus
Metrics + logs + partially missing traces + kernel.
Then ask whether kernel telemetry recovers the lost diagnostic accuracy.
That's a much stronger practical claim: kernel telemetry acts as an observability safety net.


RQ4 — What is the minimum telemetry budget required for reliable diagnosis?
Conceptually:
max (C) DiagnosticUtility(C)
subject to
CollectionCost(C)≤B
where configuration C might be:
10% trace sampling,
15s metrics,
WARN+ logs,
kernel L1 for critical services.
This produces a Pareto frontier:
collection cost vs diagnostic capability.
That is something an operator can actually use.
