## The feedback in one paragraph

The blueprint is still the heart of the work. But it needs to sit inside a **category → problem →
blueprint** hierarchy, and each blueprint needs real references. The way references were being
collected — over 100 papers, to be attached across many blueprints — **was rejected outright**:
"trying to add those papers randomly or kind of blindly to those blueprints. This does not work.
This will not work. No, I can guarantee." The replacement is depth: pick ONE category and ONE
problem, understand it yourself properly, read about 10 papers on that one thing, then write one
blueprint that is genuinely good, evaluate it, and report on it.

**The main criticism was not about the work. It was about understanding.** "You are not making a
mental model around this research. Every time you're working on a task using AI and you don't get
it, you don't digest it yourself."

That reframes the thesis: **an agent-friendly, detailed, evaluated catalog of kernel-level
problems.** Same shape as the Concordia thesis Naser shared, but agent-friendly, more detailed,
and actually evaluated.

## Task 1 — Pick the one category and the one problem

**Priority: do this first. Everything else depends on it.**

Naser's candidates, in his order of preference:

1. **latency** — "you have explored the latency problems", "one of the most important problems in
   system-level analysis", and it overlaps with CPU
2. **CPU contention** — but Sneh is also working on CPU
3. **lock** — "it doesn't really matter"

Everything must be **from the kernel point of view**. "Any problem, anything we're discussing from
the operating system point of view, not from user, because user can be huge and heavy."

**Recommendation: latency.** It is the one Naser says you already know, and we have the most

**How:** write down, in your own words, in one page: what the category covers, what problems sit

## Task 2 — Understand that problem yourself

**This is the task the feedback was actually about, and it is the one I cannot do for you.**

"Try to understand it yourself clearly. This is the most important part that I want from you."
"Without that, you cannot do anything with it. You cannot contribute anything toward that."

**How, in the order Naser gave:**

1. **Reproduce the problem deliberately.** "Even if it's needed, create a problem like that."
   We already have labelled runs for latency (`slow_db`, 11 per app). Use those first.
2. **Look at it.** "Try to visualise it with Trace Compass or other thing." Open a real trace and
   watch the latency happen. Not a summary of it — the trace.
3. **Have it explained to you.** "Ask AI to teach it to you, to teach the problem and how to use
   kernel-level data." Using AI to *learn* is endorsed. Using it to *replace* understanding is
   what was criticised.
4. **Be able to answer, without notes:** what is happening in the kernel when this problem occurs?
   Which events show it? Why those and not others? What does it look like when it is something
   else?

**Done when:** you can explain the problem and its kernel signature to Naser without reading from
a document.

## Task 3 — Ten papers for that ONE category

Not 100. Not across all blueprints. **About 10, all on the one category you picked.**

"Find 10 papers around like CPU contention, for example, or latency or lock or whatever. Choose
only one category, one type of problem."

**How:**

1. From the ~100 already collected, keep only the ones about your chosen category. Discard or
   park the rest — they are not wasted, they are just not now.
2. Review each one. "When I say read, I mean review it. You can use review with AI, that's fine."
3. For each paper, record three things and nothing more:
   - what problem it addresses
   - **which kernel events or techniques it uses to detect it**
   - whether it has a **public GitHub repo**
4. Keep the existing `research-papers-md-files/` conversion approach. It works and it is useful.

**Watch for:** the papers may name tracepoints that no longer exist. Naser caught one live —
`sched_ttwu` / "try to wake up" — "that event I think is gone forever. The Linux kernel doesn't
have that event anymore." Now only `sched_waking` and `sched_wakeup`.

## Task 4 — The GitHub repos of those papers

**Mahsa would do this before the textual references.** "Personally, if I was doing it myself, even
I prioritise that one first."

Her reasoning: a paper's *source code* shows how the symptom is actually detected, which is more
useful to a blueprint than its prose. "For detecting this symptom, you can use what they've done,
or at least get some idea."

She is also openly unsure that textual references help at all once injected into a prompt: "I
don't know how much they could be helpful when we put it or integrate it in the prompt." **That is
a testable question and we should test it rather than assume.**

**How:** for each of the ~10 papers, find the repo if it exists. Read how it detects the symptom.
Record the technique, not the code. Put the repo URL in the blueprint's references.

## Task 5 — Rewrite that one blueprint properly

Only after tasks 2–4. "When you understand this, then you can develop a very good and detailed and
accurate blueprint."

**What goes in**, per Naser and Mahsa:

- references (papers **and** GitHub repos)
- detailed explanations
- the symptoms, and **where each symptom came from** — a paper, a repo, or our own measurement
- how to visualise it
- the code / how to run it
- **a design rationale**: why the blueprint is shaped this way

That last one is Mahsa's point and it matters for the thesis: "Otherwise, it's like kind of ad hoc
design choice to say how I came up with that blueprint design."

**Keep our existing rule:** no claim enters a blueprint unmeasured. References are now a second
source alongside measurement, not a replacement for it.

## Task 6 — Evaluate it, including a NEW third arm

Naser asked for something we do not currently run:

| arm | what it means | have it? |
|---|---|---|
| no blueprint | agent uses its own knowledge | yes (`none`) |
| with blueprint | blueprint supplied, agent may also use its own knowledge | yes (`given`) |
| **blueprint only** | "force AI to not only follow your blueprint, but also don't use anything else, just your blueprint and instruction" | **NO — needs building** |

"Stop the blueprint with and without blueprint or ask or force AI agent to use only your
blueprint, if any it has, even if it has more knowledge, say focus only on my blueprint."

**Why it matters:** the `given` arm cannot separate "the blueprint helped" from "the model already
knew". The blueprint-only arm can.

**Also measure TIME, not just accuracy.** "Measure how long does it take, how long did it take,
how accurate was it with and without blueprint, the time." We already record wall seconds per
cell — it just needs to appear in the report.

**How:** add a third arm value to the harness (`arm=only`), with a system prompt that forbids
outside knowledge. Report accuracy and wall time side by side for all three.

## Task 7 — Write a report on that one problem

"Explain everything around that part, then write a report around one, that one problem. That's
it."

One document: the problem, its kernel signature, the papers, the blueprint, the three-arm results,

## Task 8 — Restructure the repo as a catalog

Naser was specific about this.

"Create a new folder, call it like blueprint catalog. And then under that, you will have
categories, but you don't have the categories yet. Just put random like category one, category
two. Under category one, there will be one HTML file, one MD file, or one folder for each problem."

```
blueprint-catalog/
  category-1-latency/
    README.md                  what this category covers
    <problem-name>/
      blueprint.md             the blueprint (one of several documents, not the only one)
      references.md            papers + GitHub repos + key points
      traces/                  zipped example traces
      README.md                read this first
```

The model he pointed at is the **Trace-with-Love / tracevizlab** layout — one folder per case.
"There's no category, there's no category, so each of them is a case, is a problem, is an
analysis." Ours differs by having the hierarchy above it.

**Note:** placeholder category names are explicitly fine for now. Do not try to invent the full
taxonomy — "I don't want you to find all of those categories now, because you don't have that
understanding of the domain, which is fine."
