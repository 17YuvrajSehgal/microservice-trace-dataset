## Main discussion — how to frame the work

- **Categorize every problem**: is it (a) kernel/OS level, (b) configuration
  level, or (c) application code/design? The catalogue needs this split.
- The CPU throttling fault is a **configuration-level** problem: cgroup CPU
  limits on a container, not broken code and not a broken kernel.
- **New story: "OS noise for agentic AI."** Agent harnesses (Codex CLI,
  Claude, etc.) sandbox their work in containers and limit resources, and
  they cap how many sub-agents/threads they spawn. When agents feel slow,
  everyone blames the LLM. If kernel traces can show that CPU caps /
  container config account for even ~5% of agent latency, that is a strong
  finding.
- Plan shape: recreate this same CPU-cap problem under an **agentic
  workload** (e.g., Codex CLI in a container with limited CPU), then find
  2–3 more similar config/kernel problems and package them into one paper.
  Done well, this could be an ICPE-style performance paper on its own.
- Naser will send **3 papers**: read the first one first (CPU-level noise —
  the main resource), second is their own OS-noise paper, third is more of a
  technical document but published. Example he showed: "OS noise mitigation
  for benchmarking web browser execution environment performance" — do the
  same, but for agentic workloads instead of browsers.
- Mahsa's suggestion: people simulate agent resource pressure by interfering
  with the transformer's KV vectors — that needs the model running locally
  (e.g., LM Studio). Naser's point: his idea does not need a local LLM; the
  analysis is about the system under the agent, not the model itself.
  Comparing local vs API-hosted LLM behavior is a nice optional extra.
