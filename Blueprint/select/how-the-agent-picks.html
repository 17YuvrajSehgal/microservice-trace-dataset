RCA Agent · how it decides

Blueprints results and how to pick right blueprint

The one idea

When one service breaks, everything that calls it slows down too — so the whole system looks sick at once. Most of those services are just stuck in line behind one. The agent follows the line back to the one root that is truly stuck, then reads what it is waiting for. That single answer picks the blueprint.

How each fault was staged

FaultHow we create itDial (mild→hard)
CPU cap Tighten the container's own CPU quota (cgroup, via docker update --cpus) 0.5 → 0.2 cores
Noisy neighbor Start a CPU-hungry container beside the services to steal CPU (stress-ng) 1 → 2 cores
Slow database Add delay in the proxy that sits in front of the DB (Toxiproxy latency toxic) 60 → 500 ms
Network path Delay & drop packets on that one container's network interface (tc netem in its netns) 40ms/0.5% → 150ms/4%
Memory cap Tighten the container's memory limit, no swap (cgroup, via docker update -m) 300 → 160 MB

What each blueprint reads from the trace

The kernel recording logs every scheduling switch, every packet, every system call. Each blueprint watches just the one kind of event that carries its fault's signature.

blueprintKernel events it readsThe tell it's after
CPU cap sched_switch victim is ready but kept off the CPU, while CPUs sit idle
Noisy neighbor sched_switch who holds the CPU while the victim waits — a new hog
Slow database socket read / write syscalls the gap from request to answer stretches on one connection
Network path net_dev_queue (TCP seq #) the same packet sent twice = a retransmission = loss
Memory cap mm_vmscan_* reclaim, oom kill the kernel reclaiming memory over and over, or killing the process

This is why the decision tree works: each branch is really a different event stream in the same recording — "waiting for CPU" is sched_switch, "waiting for an answer" is socket syscalls, "losing packets" is duplicate TCP sequence numbers, "short of memory" is reclaim. One recording, five different signatures.

The trick is the split into "starved" vs "just waiting." The one service that is starved — denied CPU, losing packets, or short of memory — is the cause. Every service that is merely sleeping, waiting for a reply, is a symptom. Blame the starved one; follow the sleepers to it.
