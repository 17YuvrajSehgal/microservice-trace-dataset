\begin{abstract}
When a coding agent is slow, the usual diagnosis is the language model. But
agents run inside containers, which come with resource limits (a fractional
CPU, a memory ceiling, an I/O budget) set by the hosting platform. We measure how much of an agent's wall-clock time these limits
silently take, using kernel tracing (LTTng) on two production agents,
\emph{Claude Code} and \emph{Codex CLI}, across 260 controlled runs. On a
well-provisioned machine the agent is ${\approx}84\%$ LLM-bound, but this
is a regime, not a law. As resources tighten the agent does not do less
work; it waits (up to $4.7\times$ longer in the stressed phase) or a process
is OOM-killed mid-task. Over-subscribing cores inflates a parallel phase by nearly $300\%$ along
a textbook queueing law; a hard memory limit below a process's footprint is
a sharp, reproducible cliff. Every effect
reproduces across both agents and agrees with the cgroup's own counters.
Which limit bites depends on the workload: a lightweight coding task trips
only the CPU cap and the below-footprint memory cliff. When an agent feels
slow, look at the resources it was given, not only the model.
\end{abstract}

\section{Introduction}

When an agentic workflow is slow, practitioners reach for the model: a
bigger context, a faster endpoint, fewer tokens. This paper measures a cost
that view cannot see. Agent harnesses such as Codex CLI~\cite{codexcli} and Claude
Code~\cite{claudecode} run their tool calls inside containers and
sandboxes. The platform that hosts them (CI runners, Kubernetes pods, shared
build machines) routinely gives those containers resource limits through
control groups (cgroups)~\cite{cgroupv2}. We ask: \emph{how much latency does the
operating system, under such a limit, add on top of the LLM?}

On a well-provisioned machine an agent is overwhelmingly LLM-bound: it
spends most of its wall time blocked on the network, waiting for the model.
But each resource limit has a threshold past which that limit, not the
model, decides how long the agent takes, or whether it finishes at all.
Kernel traces make this precise: they see the mechanism (scheduler, memory
reclaim, block layer) that application-level metrics cannot. Our
contributions are (1)~a reproducible, kernel-only method for measuring
agentic workloads (a fixed task, a cgroup, an LTTng~\cite{desnoyers2006}
trace, and the cgroup's own counters as ground truth), with a trace-based
finding that the agent is ${\approx}84\%$ LLM-bound by default; (2)~a
catalogue of four \emph{configuration-level} mechanisms of OS noise (CPU
cap, core over-subscription, memory cap, disk-I/O cap), each with a
predicted effect the data confirms and the range in which its threshold
falls; and (3)~an end-to-end test on a realistic coding task showing
\emph{which} mechanisms a lightweight agent actually trips, with every
effect validated on two unrelated agents.

\section{Related Work}

Operating-system noise (``OS jitter'') is a long-studied source of
performance variability in HPC, where background kernel activity such as
daemons and clock ticks perturbs an otherwise CPU-bound
job~\cite{petrini2003,tsafrir2005,ferreira2008,hoefler2010}, and the same
idea has been applied to web-browser benchmarking~\cite{larres2013}. Containers isolate workloads with cgroups at near-native
cost~\cite{felter2015}, yet cloud measurements still show run-to-run
variability that demands careful protocol~\cite{maricq2018,mytkowicz2009,hoefler2015}. Kernel tracing with
LTTng~\cite{desnoyers2006} has been used to attribute a thread's waiting
time to its root cause~\cite{giraldeau2016,ezzati2018}. LLM coding agents are now evaluated on real
repositories~\cite{jimenez2024,yang2024}, but their systems-level behavior
under resource limits has not been. We transfer the OS-noise lens to these agents, studying noise that is
\emph{imposed by configuration} (cgroup limits~\cite{cgroupv2}) rather
than ambient; to our knowledge this is the first kernel-trace
characterization of how container limits affect agentic AI latency and
reliability.

\section{Methodology}
\label{sec:method}

Every run executes on one fixed Google Cloud VM (Table~\ref{tab:setup}), so
the resource limit under test is the only thing that varies. On it we study
two independent production agents, Claude Code~\cite{claudecode} and Codex
CLI~\cite{codexcli}. They share no code (a Node process vs.\ a Rust/tokio
binary) and reach different models over different APIs, so running both
separates properties of agentic workloads from artifacts of one harness.

\emph{Tasks.} Each run hands the agent one small coding task in a
throwaway Git repository. A \emph{bug-fix} task provides short Python
modules with seeded bugs and a test suite the agent must make pass; an
\emph{implementation} task provides function stubs with docstring
specifications and a test suite the agent must satisfy. For Problems~2--4
the agent simply launches a fixed, instrumented workload (parallel CPU
workers, or a large file read), so the measured work is identical from run
to run. In every case the repository is regenerated byte-for-byte, the
prompt is fixed, the session is fresh, and an integrity check confirms the
agent never edited the protected test file.

\emph{Resource limits and protocol.} The agent and all of its tool
subprocesses run inside a dedicated cgroup~v2 group~\cite{cgroupv2},
recreated for each run so its counters start at zero. Each run imposes
exactly one limit (\texttt{cpu.max}, \texttt{memory.high} or
\texttt{memory.max}, or \texttt{io.max}), swept from generous to tight.
Core over-subscription (Problem~2) is the one exception: it uses no cgroup
limit and simply places more runnable threads in the group than the machine
has cores. Every condition is run five times (three for purely
observational cells) in random order, and we report
medians~\cite{maricq2018,hoefler2015}, so LLM nondeterminism and
time-of-day effects cannot line up with any one
condition~\cite{mytkowicz2009}. For the three stress experiments (cores,
memory, disk) we pre-registered the predicted direction of each effect.

\emph{Tracing and analysis.} Without modifying the agent, we record a
curated kernel LTTng~\cite{desnoyers2006} profile: all system calls plus
the scheduler, block-layer, networking, interrupt, power, and memory-reclaim
(\texttt{mm\_vmscan}) tracepoints, each tagged with process and thread. We
rebuild the agent's process tree (Figure~\ref{fig:method}) from
\texttt{root.pid} via \texttt{sched\_process\_fork}, so every spawned tool
is captured, and a per-thread state machine, in the spirit of kernel-trace
wait analysis~\cite{giraldeau2016}, labels every slice of a thread's time
as \emph{on-CPU}, \emph{runnable-but-waiting} (CPU ``noise''), or
\emph{blocked} on a named system call. We also snapshot the cgroup's own
accounting (\texttt{cpu.stat}, \texttt{memory.*}, \texttt{io.stat}) as
independent ground truth. Trace
on-CPU time agrees with \texttt{cpu.stat} to a few percent on throttled
runs (median ${\approx}2\%$), loosening to ${\approx}18\%$ on unthrottled
runs where many short-lived helper threads are mapped late; the throttle
figures we report come straight from \texttt{cpu.stat}.

\emph{Baseline: how much of a run is the model?} From the trace we identify
the API sockets (descriptors the agent \texttt{connect}s to on port 443)
and measure, per request, the interval from request write to last streamed
read; the union of these intervals is the time a model request is
outstanding. Unthrottled, the agent spends a median of \textbf{84\%} of wall-clock
time with a request in flight (80--91\% across ten runs, two tasks) and
only ${\approx}4.7$ CPU-seconds computing locally.

\section{Problem 1: CPU Cap}
\label{sec:cpu}

We cap the agent's cgroup with \texttt{cpu.max} at unlimited, 1, 0.5, and
0.25 core, for two tasks (bug-fix, implement), 5 reps each (40 runs). The
agent's compute demand is fixed at roughly 4--5 CPU-seconds whatever the
cap (Table~\ref{tab:cpu}). The cap does not reduce the work; it turns
compute into \emph{throttle wait}, the CFS bandwidth-control mechanism that
parks a group's run queue once its quota for the period is
spent~\cite{turner2010}: on-CPU time is flat while throttled and wall time
climb as the cap tightens. At 1 core the agent is still LLM-bound; at
0.5 core and below the cap substantially increases execution time. At
0.25 core throttle reaches 61\% of the implement run, though the model
still accounts for roughly half of the wall clock.

\section{Problem 2: Threads vs.\ Cores}
\label{sec:threads}

The agent launches $W \in \{2,4,8,16\}$ identical CPU-bound workers on the
4-vCPU machine with no cgroup limit, 5 reps each (20 runs). With $W$
runnable threads on $C$ cores, queueing theory~\cite{harchol2013} predicts
that each thread spends a fraction $(W-C)/W$ of its time
runnable-but-waiting. Table~\ref{tab:threads} shows a clean dose-response: per-worker on-CPU
time is flat (the work is identical) and the parallel phase inflates purely
from run-queue waiting. The measured wait
fraction matches the $(W{-}C)/W$ law almost exactly (at $W{=}8$,
$0.93/1.87=0.497$ vs.\ $0.500$; at $W{=}16$, $2.81/3.76=0.747$ vs.\
$0.750$). Scheduling stalls of $\ge 1$\uu{ms} jump from tens to thousands
once $W>C$; a $\ge 10$\uu{ms} tail, the kind of rare stall that compounds
across stages at scale~\cite{dean2013}, stays in single digits until heavy
over-subscription, reaching 138 at $4\times$. These multipliers are for the \emph{tool phase}: against the saturated
($W{=}C$) baseline it inflates $+91\%$ at $2\times$ and $+295\%$ at
$4\times$. Since the agent's own turns
dominate the run, total completion time rises less, from ${\approx}8$ to
${\approx}11$\uu{s}.

\emph{Does the harness do this to itself?} We separately asked Claude Code
to launch $N{=}4,8$ sub-agents in parallel, each running the same worker (6
observational runs), and saw little CPU contention: the sub-agents' CPU
bursts are uncontended ($\approx\!0.4$\uu{s} each, runnable-wait
${\approx}0$, ${\sim}20$ stalls vs.\ 2550 for raw over-subscription) and
staggered across the phase, each blocked on its own LLM turn rather than
fighting for a core. The contention above is thus real but needs
\emph{explicit} over-parallelism (e.g.\ \texttt{xargs -P} or an
under-provisioned shared box) rather than the default sub-agent path.

\section{Problem 3: Memory Cap}
\label{sec:mem}

We press the agent's memory from two directions, because the kernel's
response depends on whether the pressured memory is \emph{reclaimable}. The
agent plus a 1\,GB file working set~\cite{denning1968} is
${\approx}1.38$\,GB. Part~A varies the soft limit \texttt{memory.high}~\cite{cgroupv2}
(throttles, never OOM-kills) on a file-reading workload (20 runs). Part~B
varies the hard limit \texttt{memory.max}~\cite{cgroupv2} (OOM-kills when
usage cannot be reduced), first on the same file workload (12 runs) and
then on a 512\,MB anonymous-allocation workload (12 runs).

\emph{Part A: recoverable slowdown.} With a soft cap above the working set
the file stays cached (zero refaults); below it every pass re-reads from
disk, ${\approx}1.05$ million page refaults and a $4.7\times$ slower read
phase (Table~\ref{tab:mem}). The transition falls between the 1536 and
1152\,MB caps we test. The reclaim CPU stall is tiny
(${\approx}0.16$\uu{s}); the cost is the refault I/O. The soft cap
throttles the group (8--9k \texttt{memory.high} events) but never kills
it.

\emph{Part B: the OOM cliff.} On the file workload, even a tight
\texttt{memory.max} (down to 768\,MB) causes \emph{no} OOM kill: clean page
cache is always reclaimable, so the kernel reclaims it (paying the same
refault cost) instead of killing. The cliff requires \emph{unreclaimable}
(anonymous) memory. On the 512\,MB anonymous workload (agent + workload
${\approx}762$\,MB, $n{=}3$ per cap) the outcome is a sharp, reproducible
step: at \texttt{memory.max} of 1024, 896, and 768\,MB no run is killed
and every task succeeds (0/3 OOM, 0/3 fail); at 640\,MB every run is
OOM-killed and fails (3/3, 3/3). The cliff lies between 640 and 768\,MB. Notably, the OOM killer takes the \emph{worker} (the largest
anonymous consumer), not the node process; the agent survives, detects the
\texttt{SIGKILL}, and reports the correct reason without retrying. A
sandbox memory limit can thus silently kill the agent's tools mid-task
while the agent keeps running.

\section{Problem 4: Disk-I/O Cap}
\label{sec:io}

We cap the cgroup's read bandwidth with \texttt{io.max}
\texttt{rbps}~\cite{cgroupv2} at unlimited, 200, 100, and 50\uu{MB/s} on a
cold 1\,GB single-read workload (caches dropped first), 5 reps each (20
runs). Once the cap drops below native disk speed, the read phase scales
inversely with the cap (Table~\ref{tab:io}): \texttt{io.stat} shows the
same ${\approx}1.23$\,GB moved in every cell (the 1\,GB file plus
read-ahead) while the phase grows $1.7\times$ at 100\uu{MB/s} and
$3.4\times$ at 50\uu{MB/s}. Device throughput (bytes over phase) tracks the cap, a little above it
because read-ahead is issued before throttling engages. The 200\uu{MB/s} cap has no effect: the disk's
own sequential rate is only ${\approx}205$\uu{MB/s}, so a cap at or above
it cannot throttle.

Problems~1--4 isolate each mechanism with a workload built to stress it. To
see which a lightweight agent actually trips, we ran the \emph{implement}
task end-to-end under each limit and recorded completion time and success
(Table~\ref{tab:e2e}; $n{=}3$; CPU and unlimited rows from Problem~1). Only the CPU cap meaningfully
slows the task. A disk cap down to 20\uu{MB/s} has no effect: the task
reads a handful of small files and is not I/O-bound. A memory cap has
no effect either until it drops below the agent's own footprint
(${\approx}340$\,MiB peak, mostly reclaimable page cache): Claude survives
down to 192\,MiB by reclaiming cache, but at 128\,MiB the node process
itself enters the kill path and \emph{thrashes}, spawning processes that are
OOM-killed repeatedly (six kills across three runs), running $7\times$
longer, and mostly failing; at 96\,MiB it is $30\times$ slower and fails
every time. Unlike the tool-OOM case of Problem~3, where the agent survives
and reports cleanly, here the agent is killed mid-run and produces no
report. The failure point tracks the agent's footprint: the leaner Codex
(Rust) survived every cell, including 96\,MiB (its wall times are
API-dominated, so we report it by outcome). In short, a
lightweight coding task hits only the CPU cap and the below-footprint
memory cliff; memory- and disk-heavy agent work (builds, data pipelines)
would trip the rest.

\section{Discussion}
\label{sec:consistency}

\emph{The effects are not tied to one harness.} We repeated all four
problems with Codex CLI (130 runs, at parity with Claude).
Scheduling, memory-reclaim and I/O results are identical to within noise
(Claude vs.\ Codex medians: $W{=}16$ phase 3.9 vs.\ 3.8\uu{s} and
runnable/worker 2.8 vs.\ 2.8\uu{s}; 768\,MB refault phase 30.4 vs.\
30.4\uu{s}; 50\uu{MB/s} read 20.4 vs.\ 20.4\uu{s}), because those workloads
are fixed workers the agent merely launches. CPU-cap results show
the same trend (0.25-core throttle 19.8 vs.\ 18.7\uu{s}; model share of
wall 53 vs.\ 62\%): both agents are ${\ge}80\%$ LLM-bound uncapped and
shed that share under tighter caps. The one difference: the OOM cliff sits
at \emph{agent RSS $+$ workload}, so the leaner Rust harness survives a
640\,MB cap that kills the Node harness (${\approx}250$\,MB RSS).

\emph{It is not just the LLM; the exposure is in the configuration.}
Blaming the model is understandable at ${\approx}84\%$ LLM-bound, but a
tight container limit on a resource the workload uses adds
$1.7$--$4.7\times$ to the affected phase or kills a process outright, at
sandbox sizes common in practice (fractional-CPU CI runners, tight memory
pods). The harness did not over-subscribe the CPU itself (Section~\ref{sec:threads}), so the exposure comes from the limits
the environment grants, exactly the parameter nobody profiles when an agent
``feels slow.'' The harms come in two shapes with different remedies:
bandwidth limits (CPU, disk, soft memory) cause \emph{recoverable slowdown}
(right-size the cap), while a hard limit on an unreclaimable resource
(anonymous memory, no swap) causes \emph{failure} (add headroom).

\emph{Counters say what, the trace says where.} Cgroup counters report the
8505 \texttt{high} events and 1.05\,M refaults of a capped run, but only the
trace shows the refaults are the file-read tool blocking on block I/O while
the agent is untouched, and only the trace attributes 84\% of an uncapped
run to the model's socket, the familiar gap between aggregate metrics and
kernel-level cause~\cite{ezzati2018}.

\emph{Limitations.} The main uncontrolled input is LLM nondeterminism,
mitigated by fixed prompts, byte-identical repos, random order, and medians. Deterministic metrics (tool-phase time, throttle, refaults, OOM
outcomes) reproduce to within a few percent across reps; total wall time
varies more (up to ${\approx}15\%$) because it includes the model's
round-trips. The findings are tied to one machine shape (no swap, so anonymous
pressure OOMs rather than swaps; an SMT topology; one disk speed, which
sets the I/O knee) and to small tasks (Section~\ref{sec:e2e}).

\section{Conclusion}

An AI coding agent is ${\approx}84\%$ LLM-bound on a well-provisioned
machine, but a tight container limit on CPU, cores, memory, or disk I/O can
add up to $4.7\times$ to the affected phase or kill a process mid-task. We characterized four such mechanisms with kernel traces, bounded each
threshold, validated them against the kernel's own counters, reproduced
them on a second agent, and showed which ones a realistic task hits. When
an agent feels slow, profile the sandbox, not only the model.
