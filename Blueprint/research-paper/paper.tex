\title{\vspace{-2em}\bfseries OS Noise for Agentic AI:\\
A Kernel-Trace Study of How Container Resource Limits\\
Slow Down and Break AI Coding Agents}

\author{Yuvraj Sehgal \quad Naser Ezzati-Jivan\\
\small Department of Computer Science \quad (draft --- \today)}
\date{}

\begin{abstract}
AI coding agents feel slow, and the blame almost always falls on the large
language model (LLM). We ask a different question: how much of an agent's
wall-clock time is spent not on the model but on the \emph{operating system
underneath it}, when the agent runs in a resource-limited container?
Using kernel tracing (LTTng) on a single controlled virtual machine, we
profile a production agent (Claude Code) under four classes of
configuration-level resource limit: a CPU-bandwidth cap, CPU
over-subscription (more parallel workers than cores), a memory cap, and a
disk-I/O bandwidth cap. Across 130 traced runs we find that an agent's own
compute demand is small and fixed; a mis-configured limit does not make the
agent do less work, it makes the agent \emph{wait} (1.7--4.7$\times$ slower)
or \emph{die} (its tools are OOM-killed mid-task). The effects are a
\emph{regime}: agents are LLM-bound on an adequate machine and become
OS-bound only past a per-resource threshold, which we locate for each
resource. Every effect is visible in both the kernel trace and the
control group's own counters, and is cross-validated between them
(trace-measured on-CPU time matches \texttt{cpu.stat} to 97--99.7\%). We
also show that a well-behaved harness checks the core count and does
\emph{not} over-subscribe the CPU on its own---so the danger lies in the
configuration a platform imposes, which is exactly what no one profiles.
\end{abstract}

\section{Introduction}

When an agentic workflow is slow, practitioners reach for the model: a
bigger context, a faster endpoint, fewer tokens. This paper measures a
cost that is invisible to that view. Agent harnesses (Codex CLI, Claude
Code, and similar) run their tool calls inside containers and sandboxes,
and those containers are routinely given resource limits---a fractional
CPU, a memory ceiling, an I/O budget---by the platform that hosts them
(CI runners, Kubernetes pods, shared build machines). We ask: \emph{how
much latency does the operating system, under such a limit, add on top of
the LLM?}

Our thesis is a regime statement rather than a blanket one. On an adequate
machine an agent is overwhelmingly LLM-bound: it spends most of its wall
time blocked on the network, waiting for the model. But each container
resource limit has a threshold past which the \emph{configuration}, not the
model, dominates. We make this precise with kernel traces, which see the
mechanism (scheduler, reclaim, block layer) that application-level metrics
cannot.

\paragraph{Contributions.}
\begin{itemize}\itemsep1pt
  \item A reproducible, kernel-only measurement method for agentic
  workloads: a fixed task, a control group, an LTTng trace, and the
  cgroup's own counters as ground truth, with trace/counter
  cross-validation.
  \item A four-problem catalogue of \emph{configuration-level} OS noise for
  a real agent---CPU cap, thread/core over-subscription, memory cap, and
  disk-I/O cap---each with a pre-registered hypothesis that the data
  confirms.
  \item Quantified thresholds and two qualitatively distinct harms
  (recoverable slowdown vs.\ catastrophic failure), plus evidence that a
  production harness does not self-inflict the CPU-contention variant.
\end{itemize}

\section{Related Work}

Operating-system noise (``OS jitter'') is a long-studied source of
performance variability in HPC and in benchmarking, where background kernel
activity perturbs an otherwise CPU-bound job. Recent work has carried the
idea to user-facing settings; for example, OS-noise mitigation has been
studied for benchmarking web-browser execution environments. We transfer
the lens to a new and rapidly growing workload---LLM-driven coding
agents---and, crucially, study noise that is \emph{imposed by
configuration} (cgroup limits) rather than ambient. To our knowledge this
is the first kernel-trace characterization of how container resource limits
affect agentic AI latency and reliability.

\section{Methodology}
\label{sec:method}

\paragraph{Platform.} All runs execute on one Google Cloud VM
(\texttt{n2-standard-4}): Intel Xeon @ 2.80\,GHz, 4 vCPUs (2 physical cores
$\times$ 2 SMT threads), 15\,GiB RAM, no swap, a \texttt{pd-balanced} boot
disk (${\approx}205$\uu{MB/s} native sequential read), Ubuntu 24.04.5,
kernel \texttt{7.0.0-gcp}, LTTng 2.15.3, Babeltrace2. All performance
numbers come from this VM only. We deliberately use one machine so that
condition is the only thing that varies.

\paragraph{Agent and tasks.} The agent is Claude Code run headless
(\texttt{claude -p}) on small, fixed coding tasks (fix seeded bugs across a
few Python modules; implement functions from a specification; run a
controlled parallel or I/O workload). Each run regenerates a
\emph{byte-identical} task repository, uses a fixed prompt, and is a fresh
agent session. An integrity check records whether the agent modified the
protected test file; no accepted run did.

\paragraph{Isolation and limits.} The agent (and its tool subprocesses) run
inside a cgroup~v2 group. We set exactly one limit per run---\texttt{cpu.max},
\texttt{memory.high}/\texttt{memory.max}, or \texttt{io.max}---and recreate
the group each run so its counters start at zero. CPU over-subscription
(Problem~2) uses no limit at all: it is purely a workload with more runnable
threads than cores.

\paragraph{Tracing and ground truth.} We record a curated kernel LTTng
profile (all system calls; the \texttt{sched\_*}, \texttt{block\_*},
\texttt{net/skb/sock/tcp}, \texttt{irq/softirq}, \texttt{power\_*}, and
\texttt{mm\_vmscan\_*} tracepoint families) with per-event pid/tid/procname
and namespace context. No user-space instrumentation is used; the agent is
not modified. Alongside the trace we snapshot the cgroup's own counters
(\texttt{cpu.stat}, \texttt{memory.stat}/\texttt{memory.events}/
\texttt{memory.peak}, \texttt{io.stat}) before and after, plus
\texttt{CLOCK\_REALTIME}/\texttt{MONOTONIC}/\texttt{BOOTTIME} anchors.

\paragraph{Analysis.} From \texttt{root.pid} we reconstruct the agent's
process subtree via \texttt{sched\_process\_fork}, then run a per-thread
state machine over \texttt{sched\_switch}/\texttt{sched\_wakeup} to attribute
every slice of time to \emph{on-CPU}, \emph{runnable-but-waiting} (the CPU
``noise''), or \emph{blocked} (off-CPU, bucketed by the blocking system
call). Reclaim stalls are bracketed from \texttt{mm\_vmscan} reclaim
begin/end events. Each metric is validated against the matching cgroup
counter.

\paragraph{Statistics.} We run 5 repetitions per condition (3 for purely
observational cells), randomize run order, and report medians, so that LLM
nondeterminism and time-of-day effects do not align with any one condition.
Hypotheses are pre-registered per problem before the campaign.

\paragraph{Validation.} As a correctness check on the trace pipeline,
trace-measured subtree on-CPU time matches the kernel's own
\texttt{cpu.stat} accounting to within 0.1--3\% on every run
(e.g.\ 3.26\,s vs.\ 3.27\,s on a 1-core run).

\section{Problem 1: CPU Bandwidth Cap}
\label{sec:cpu}

\paragraph{Setup.} We cap the agent's cgroup with \texttt{cpu.max} at
unlimited, 1, 0.5, and 0.25 core, for two tasks (bug-fix, implement),
5 reps each (40 runs).

\paragraph{Result.} The agent's compute demand is fixed---roughly
4--5 CPU-seconds regardless of the cap. The cap does not reduce the work; it
converts compute into \emph{throttle wait}. Table~\ref{tab:cpu} and
Figure~\ref{fig:cpu} show both tasks: on-CPU time is flat while throttled
time and wall time climb as the cap tightens.

\section{Problem 2: Threads vs.\ Cores}
\label{sec:threads}

\paragraph{Setup.} The agent launches $W \in \{2,4,8,16\}$ identical
CPU-bound workers on the 4-vCPU machine (no cgroup limit), 5 reps each
(20 runs). With $W$ runnable threads on $C$ cores, queueing theory predicts
each thread spends a fraction $(W-C)/W$ of its time runnable-but-waiting.

\paragraph{Result.} Table~\ref{tab:threads} and Figure~\ref{fig:threads}
show a clean dose--response. Per-worker on-CPU time is flat (identical work);
the parallel phase inflates purely from run-queue waiting. The measured wait fraction matches the
$(W{-}C)/W$ law almost exactly: at $W{=}8$, $0.93/1.87=0.497$ vs.\ a
predicted $0.500$; at $W{=}16$, $2.81/3.76=0.747$ vs.\ $0.750$. Scheduling
stalls $\ge 1$\uu{ms} explode once $W>C$ (from tens to thousands), and a
$\ge 10$\uu{ms} tail appears only in the over-subscribed regime.

Phase-wall inflation versus the saturated ($W{=}C$) baseline is $+91\%$ at
$2\times$ and $+295\%$ at $4\times$ over-subscription.

\paragraph{Does the harness do this to itself?} We separately asked Claude
Code to launch $N{=}4,8$ \emph{sub-agents} in parallel, each running the
same worker (6 observational runs). The harness \emph{probes the machine}
(exactly 18 \texttt{sched\_getaffinity}/\texttt{sysinfo} calls per run,
$N$-independent) and does \emph{not} over-subscribe the CPU: the sub-agents'
CPU bursts are uncontended ($\approx\!0.4$\uu{s} each, runnable-wait
${\approx}0$, ${\sim}20$ stalls vs.\ 2550 for raw over-subscription) and
staggered across the phase, each sub-agent blocked on its own LLM turn
rather than fighting for a core. The contention of Problem~2A is therefore
real but requires \emph{explicit} over-parallelism (e.g.\ \texttt{xargs -P},
a forced concurrency setting, or an under-provisioned shared box)---not the
default sub-agent path. (Confirms H2--H3; H1 observed.)

\section{Problem 3: Memory Cap}
\label{sec:mem}

\paragraph{Setup.} We press the agent's memory from two directions, because
the kernel's response depends on whether the pressured memory is
\emph{reclaimable}. The agent plus a 1\,GB file working set is
${\approx}1.38$\,GB. Part~A varies the soft limit \texttt{memory.high} on a
file-reading workload (20 runs); Part~B varies the hard limit
\texttt{memory.max}, first on the same file workload (12 runs) and then on a
512\,MB anonymous-allocation workload (12 runs).

\paragraph{Part A --- recoverable slowdown.} With a soft cap above the
working set the file stays cached (zero refaults, ${\approx}6.5$\uu{s});
below it, every pass re-reads from disk---${\approx}1.05$ million page
refaults and a $4.7\times$ slower phase (${\approx}30$\uu{s}), see
Table~\ref{tab:mem} and Figure~\ref{fig:memory}(a). The reclaim \emph{CPU} stall is tiny
(${\approx}0.16$\uu{s}); the cost is the refault \emph{I/O}. The soft cap
throttles the group (8--9k \texttt{memory.high} events) but never kills it.

\paragraph{Part B --- a hard cap does not always kill.} On the
\emph{file} workload, even a tight \texttt{memory.max} (down to 768\,MB)
causes \emph{no} OOM kill: clean page cache is always reclaimable, so the
kernel reclaims (paying the same refault cost) instead of killing. The OOM
cliff requires \emph{unreclaimable} (anonymous) memory.

\paragraph{Part B --- the OOM cliff.} On the 512\,MB anonymous workload
(agent + workload ${\approx}762$\,MB), the outcome is a sharp, reproducible
step (Table~\ref{tab:cliff}, Figure~\ref{fig:memory}(b)):
\texttt{memory.max} of 1024/896/768\,MB all succeed (3/3), while
640\,MB fails (3/3) with an OOM kill and a failed task. Notably the OOM
killer takes the \emph{worker} (the largest anonymous consumer), not the
node process, so the agent \emph{survives and reports the failed task}
rather than crashing---``your sandbox memory limit silently kills your tools
mid-task.'' (Confirms H1--H4.)

\section{Problem 4: Disk-I/O Bandwidth Cap}
\label{sec:io}

\paragraph{Setup.} We cap the cgroup's read bandwidth with \texttt{io.max}
\texttt{rbps} at unlimited, 200, 100, and 50\uu{MB/s} on a cold 1\,GB
single-read workload (caches dropped first), 5 reps each (20 runs).

\paragraph{Result.} Phase wall scales as $\text{bytes}/\text{rbps}$ once the
cap drops below native disk speed (Table~\ref{tab:io},
Figure~\ref{fig:io}): the worker reads
1\,GB in 20.4\uu{s} at a 50\uu{MB/s} cap (an exact 50\uu{MB/s}) and
10.1\uu{s} at 100\uu{MB/s}. \texttt{io.stat} confirms the same bytes
moved in every cell, so the growth is pure throttling.

see the effect. (Confirms H2--H3.)

\section{Discussion}

\paragraph{It is not just the LLM.} Across four independent resources a
single mis-set container limit adds $1.7$--$4.7\times$ wall time or kills the
agent's tools outright---far above the ``even 5\% would be significant''
bar for this class of finding, at sandbox sizes that are common in practice
(fractional-CPU CI runners, tight memory pods).

\paragraph{Two shapes of harm.} Bandwidth limits (CPU, disk, and soft
memory) cause \emph{recoverable slowdown}; a hard limit on an unreclaimable
resource (anonymous memory, no swap) causes \emph{failure}. CPU
over-subscription is a third, \emph{self-inflicted} slowdown. A fault
catalogue for agents should distinguish these, because they call for
different remedies (right-size vs.\ add swap/headroom vs.\ bound
concurrency).

\paragraph{Configuration is the villain, not the harness.} Because a
well-behaved harness checks cores and avoids CPU over-subscription
(Section~\ref{sec:threads}), the danger is concentrated in the limits a
platform imposes---exactly the parameter nobody profiles when an agent
``feels slow.''

\paragraph{Everything is kernel-visible.} Each effect appears in both the
LTTng trace and the cgroup's own counters, and the two agree. This makes the
method a reusable recipe for a larger fault catalogue rather than a set of
one-off anecdotes.

\section{Threats to Validity}

\emph{Construct.} Our ``event-loop wait'' bucket conflates true LLM-network
wait with idle, because the agent's \texttt{epoll\_pwait2} return is not
decoded to a specific file descriptor on this kernel; our headline results
(throttle, refault, OOM, I/O) do not depend on that split.
\emph{Internal.} LLM nondeterminism is the main uncontrolled input; we
mitigate with fixed prompts, byte-identical repos, randomized order, and
medians of 5. \emph{External.} A single VM, one agent, and small tasks limit
generalization; the no-swap configuration makes anonymous pressure OOM
rather than swap, and the SMT topology means the effective zero-contention
core count is 2--4. We state the machine's native disk speed because it sets
where the I/O knee falls. \emph{Conclusion.} Each result is reproducible to
$<\!1\%$ across reps and cross-validated against an independent kernel
counter.

\section{Conclusion}

An AI coding agent is LLM-bound on an adequate machine, but a single
mis-configured container limit---on CPU, cores, memory, or disk I/O---pushes
it into an OS-bound regime where the operating system, not the model, is the
bottleneck, adding up to $4.7\times$ latency or killing the agent's tools.
We characterized four such configuration-level problems with kernel traces,
located each threshold, and validated every measurement against the kernel's
own accounting. The practical message is blunt: when an agent feels slow,
profile the sandbox, not only the model.
