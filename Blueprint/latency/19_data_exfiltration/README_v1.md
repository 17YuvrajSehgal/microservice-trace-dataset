# Blueprint: one process pushes a lot of data out, one way (bulk transfer)

| | |
|---|---|
| Problem class | Security / capacity (the network is healthy and is being used heavily) |
| Root cause this blueprint confirms or rejects | One process sends a large, steady stream to one destination and almost nothing comes back |
| Evidence | An LTTng kernel trace only, with `net_dev_queue` |
| Not used | Logs, metrics, packet contents |

**When to use this.** Outbound traffic is well above normal and nothing is broken: no loss,
no errors, normal latency. Or someone asks "is anything on this host shipping data out?".

> **Honest status.** Calibrated on 10 labelled `data_exfiltration` runs (5 Sock Shop, 5 Train
> Ticket; a container sending 40 MB/s of generated bytes to a sink container on the same host)
> and checked on the other 293 runs of both applications. The labelled workload is a harmless
> simulation: only the shape is real.

---

## Part 1. Background

Every other network blueprint looks for damage (drops, retransmits, delay). Here there is
none. What a bulk transfer has is three things together:

| | bulk transfer | service traffic | telemetry export |
|---|---|---|---|
| volume of one stream | **42 MB/s** | under 0.3 MB/s | 1-3 MB/s |
| payload coming back | **0.0%** | 250-400% (replies are bigger than requests) | 0.1% |
| flows in every second | **yes** | yes | yes |

So direction alone is not enough: telemetry export and a database result stream are one-way
and steady too (largest measured outside the fault: 2.96 MB/s). Volume alone is not enough
either on a busier system. The verdict needs all three.

A stream is counted per process and destination, not per host. The host total does not
transfer between applications (measured earlier: the same transfer is 6x the baseline on one
application and 25x on the other).

## Part 3. Procedure

### Step 1. Orient
```bash
python3 $TOOLS/idx_summary.py $TRACE --rate 10 | sed -n '/^data written per/,$p'
```
Pick a time inside the suspect window (`T`).

### Step 2. One network slice
```bash
bash $TOOLS/extract_slice.sh $TRACE $DAY $T 10 $WORK/net.txt 'net_dev_queue'
```

### Step 3. The decisive check
```bash
python3 $TOOLS/egress.py $WORK/net.txt 10
```

| Verdict line | Meaning |
|---|---|
| `VERDICT: BULK ONE-WAY TRANSFER: <comm> (pid P, pid_ns N) sends X MB/s from A to B:port, 0.0% comes back, flows in 100% of the seconds, S% of all TCP payload in the slice` | **This fault.** That process is the sender, `B:port` is where the data goes |
| `VERDICT: NO BULK ONE-WAY TRANSFER (largest steady one-way stream: X MB/s by <comm> ...; the bar is 5 MB/s)` | Not this fault. The table above the verdict lists the biggest streams |

The table has one row per stream: `MB/s`, `back` (payload coming back as a share of the
payload sent), `active` (share of the seconds in which it flows), the sender, and the
destination.

### Step 4. Rule out a losing path
A path that drops packets also moves many bytes, because it sends the same bytes again.
```bash
python3 $TOOLS/net_loss.py $WORK/net.txt 10
```
If it reports dropped segments, go to blueprint 5 instead.

### Step 5. When did it start
Cut the same slice 60 s and 120 s earlier and run Step 3 again. The first slice with the
verdict is the start of the incident window.

### Step 6. Submit
- `fault_type`: `data_exfiltration`.
- `root_cause_service`: the process and container from the verdict line (`comm`, `pid_ns`).
- `incident_window`: from the first slice with the verdict to the end of your last slice.
- `evidence`: the verdict line word for word.
- Fix: find out what the process is and whether the transfer is expected; then throttle or block it.

## Part 4. Measured, and limits

- Per-run lines: `RESULTS.md` next to this file. 10 of 10 labelled runs, 0 false alarms in 293
  other runs. Smallest labelled stream 41.9 MB/s; largest steady one-way stream elsewhere
  2.96 MB/s (a proxy relaying database results on Train Ticket).
- **The 5 MB/s bar is not safe for a slow transfer.** The recipe has a 5 MB/s setting that
  was never collected. It would sit on the bar, less than 2x above normal telemetry. A slow
  leak needs a baseline (the same stream an hour earlier), which this tool does not do.
- **The trace cannot say the transfer is unauthorised.** A backup or a log shipper has the
  same shape. The verdict names the shape; a person decides.
- Only TCP over IPv4 is counted. A transfer over UDP or IPv6 is not seen.
- In the labelled runs the destination is a container on the same host. A real destination
  off the host shows the same events on the outgoing interface, but that path was not measured.
