The idea

A finished investigation, written down so it can be run again

Today an engineer solves a hard problem and the knowledge leaves with them. A blueprint captures the whole investigation as one document.

What to collectthe exact events needed — named, not described
→
What to runthe analysis steps, as runnable commands
→
What the answer ishow to decide, and when to stop
⇒
One JSON document a person or an agent can execute it — next time the problem appears

What one looks like

One file. Six questions answered.

// cpu-contention-co-tenant.json (shortened) "applicability": { "apply_when": ["several unrelated services slow down together"], "do_not_apply_when": ["only one service is affected"] } "collection_order": { "kernel_events": ["sched_waking", "sched_switch"], "window": { "baseline_s": 60, "incident_s": 120 } } "processing": [ { "step": "measure how long threads waited for a CPU (Runqueue delay)", "capability": "kernel.scheduler.runqueue_delay (Database poll wait)" } ] "decision": { "verdict_when": ["wait time up several-fold, many processes"], "rule_out": [{ "instead": "waiting on a dependency" }] } "stopping_conditions": { "stop_and_switch": "one component blocked 10x -> other blueprint" } "policies": { "max_collection_overhead_pct": 5, "requires_approval": ["tracing above 3% overhead"] } "evidence_sufficiency": { "confidence_floor": 0.7 }
When does this apply?and just as important, when it does not
What do I collect?exact event names — two, not “kernel data”
What do I run?a capability, bound to whichever tool you already have
How do I decide?what makes it true — and what to prefer instead
When do I stop?including “this is the wrong blueprint, use that one”
What am I allowed to do?your overhead budget and approval rules

Every claim in the file carries the measurement that proved it. Signals we tested and found useless stay in, marked “does not work”.

The test we set ourselves

Two problems that look identical from outside

CPU contention

Another workload on the same machine steals CPU. Your services aren’t busy — they’re waiting for a turn.

Slow datastore

The database answers slowly. It isn’t busy either — it’s blocked waiting on something else.

Both look the same on a dashboard: things are slow, nothing is obviously broken.

Measurement from the kernel traceCPU contentionSlow datastore
How long threads waited for a CPU (Runqueue delay) 7.1×1.0×

Same two measurements. Opposite answers. That is what makes the two problems separable — and what the blueprint encodes.

How a blueprint is built

Signals are measured, never guessed

We don’t write these from intuition, and we don’t let a model invent them. Every signal in a blueprint has been proven on real, labelled failures first.

Labelled failuresfaults we injected on purpose, plus published RCA datasets
→
Mining scriptssearch for signals that are specific to one problem
→
Proven signalonly what separates this problem from its look-alikes
→
Blueprintwith the evidence attached
Our own first draft had three signals that sounded obviously right. Measuring 93 real failures killed all three. They are kept in the blueprint, marked as “does not work”, so nobody tries them again.

Why ours dropped, and why that is useful. On the shop app the database polls constantly, so a delay showed up straight away. On the booking app, long-lived pooled connections mean it sits idle instead and the same signal goes quiet. One feature cannot catch every database problem — and the two strong methods turn out to be opposites: the kernel finds what metrics cannot, and the reverse.

The AI agent is beaten by both. Across all 10 CPU-contention failures on both systems it named the cause correctly zero times; the blueprint got 9. Knowing which method fits which problem is the valuable part — and that is what a blueprint stores.
