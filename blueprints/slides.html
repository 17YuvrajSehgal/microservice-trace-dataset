01 The idea

Trace analysis should accumulate, not restart

Every investigation decides what data to collect, what analysis to run, and what the answer is. Today all of that is discarded when the ticket closes — the knowledge stays in one engineer's head.

A blueprint

Writes one solved investigation down so it can be re-executed — by a person or an agent. Blueprints build into a library.

Not a runbook

Exact event names, runnable steps, an output specification, and machine-checkable stopping conditions. Written to run without a human.

Not the agent

The agent is the instrument. The contribution is the reusable knowledge object and the evidence that it works again.

02 What we built

Two problems, chosen to be opposites

Both look identical from outside: things are slow, nothing is obviously broken. If the method can separate these two, it is worth something.

CPU contention

Another workload on the same machine steals CPU. Services are not busy — they are waiting for a turn on the processor.

Datastore wait

A database answers slowly. It is not busy either — it is blocked waiting on something below the traced layer.

03 The discipline caught us

Our first draft was wrong — measurement killed three claims

Rule: nothing enters a blueprint until it is measured on our own data. We wrote v1 from what we believed, then measured 93 runs / 310 records.

We had writtenWhat the data showed
services show raised runnable-wait never exceeds 4% in any fault — and was 1.6% on the very run it described
the culprit’s wait breakdown identifies it no culprit record exists at all for host-level faults — 5 families
the datastore shows dominant external-I/O wait true — and 98–99% for every fault type. Identifies nothing

Why they failed

The derived summaries report shares of time, and idle waiting swamps them. Every service looks the same.

What we changed

Read the raw LTTng trace with Babeltrace2 instead. Per-event latencies, not shares — and the signal appeared.

Killed claims are kept

Retracted signals stay in the blueprint with the measurement that killed them, and reach the agent as “do not reason from this”.

04 The result measured

The same measurement, opposite answers

Signal, from the raw kernel trace CPU contention Datastore wait
Runqueue delay — busiest service, p95 7.12× 0.97×
Runqueue delay — median across processes 1.78× 0.84×
Database poll wait, p95 1.12× 36.83×
Trace convergence on one component none 717.7×

Read row three. Same measurement, same component — 1.12× against 36.83×. That is what makes the two blueprints genuinely separable.

Datastore blueprint, run on the CPU fault: NO — no socket-waiting syscall inflated by 5× or more (largest 3.95×). Runqueue delay inflated up to 7.12× — the processes are short of CPU. Use the CPU-contention blueprint.

It refuses to answer and routes to the right blueprint. On the datastore fault it also reports, unprompted: “traces name catalogue, but the kernel shows mysqld is the one blocked — catalogue is a victim.” That is our blind-spot argument, found by the tool.

The slow-database case, both ways

Shop app: metrics 0/7, kernel 5/7 — the database goes idle while blocked, so metrics see nothing.
Booking app: metrics 7/7, kernel 0/7 — pooled connections silence the kernel signal instead.

What actually holds

The kernel layer earns its place exactly where metrics go quiet. Not "kernel beats metrics" — they are near-perfectly complementary, and now we can say which to use when.

Unchanged across both apps

No LLM setup ever named the cause of CPU contention correctly — 0 of 10. It finds the right component, then calls it saturation or throttling. The blueprint got 9 of 10.

A simple statistical baseline beats us overall, 71% to 58%. Reporting that is the point: the two approaches fail in different places, which is knowledge a blueprint library should encode — not something to hide.

06 Where we are

The knowledge is built and proven. The runtime is next.

Built

  • Blueprint format + validator that enforces the rules
  • Two blueprints, fully measured, evidence stored
  • Five analysis scripts on the raw kernel trace
  • Blueprint → agent-skill generator
  • Capability → tool registry with cost metadata

Not built

  • The runtime: intent → selection → binding → execution
  • The with/without-blueprint experiment
  • Mining blueprints from past tickets
  • Selection is manual today

Not claiming

  • One run per fault — repeats owed
  • Two problems, not the five eventually wanted
  • Process-name attribution is ambiguous on Java services
