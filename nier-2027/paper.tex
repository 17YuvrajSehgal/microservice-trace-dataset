\title{Context Is a Pipeline, Not a Window:\\
Information Attrition in LLM Agent Harnesses}

\author{\IEEEauthorblockN{Anonymous Author(s)}
\IEEEauthorblockA{Submitted for double-anonymous review}}

\maketitle

\begin{abstract}
LLM agents are judged by two numbers: how large the context window is, and how
often the final answer is right. Both miss a third thing: how much of a
tool's output is lost before the model ever sees it. We measured this in a
tool-using agent that diagnoses faults from kernel traces. The window was
almost empty: the largest single prompt across $720$ runs used only
$5.75\%$ of it. Yet a third of all tool results ($3{,}827$ of $11{,}189$)
were cut in transit, and every cut result was broken JSON. The loss followed
a pattern. The harness cut results by slicing the JSON text at a fixed
length, and a slice like that deletes whatever sits late in the text. One
field reached the model in $4.7\%$ of calls; its neighbour, in the same
results, reached it in $99.3\%$. Which field holds the culprit depends on
whether the culprit process started during the trace, and the benchmark's
accuracy split matched that line exactly. So we ran controlled experiments to
test whether the cut \emph{caused} the split. This paper contributes a model
of agent context as a five-stage pipeline, with a way to measure loss at each
stage; replays of $864$ real tool results, including a production trace
where the shipped cut deletes all $128$ records of the culprit's class; an
experiment showing the cut's cost arrives as extra work before it arrives as
errors ($28\%$ more tool calls, double the computations, yield falling from
$0.61$ to $0.31$), while the answer survives when the agent has other ways
to reach it; and a survey of seven agent frameworks that finds this same
position-based cut in two of them, with no consistent alternative in the
rest. Whether the cut causes the accuracy split is still an open question. A
repeated production-trace replay moves the same way, but it does not settle
it.
\end{abstract}

\begin{IEEEkeywords}
LLM agents, agent harnesses, context engineering, empirical evaluation
\end{IEEEkeywords}

\section{Introduction}
\label{sec:intro}

An agent does not read its context window. It reads what its harness, the
code running around the model, decided to put there. Between a tool
producing a result and the model seeing it, the harness serializes the
result, cuts it to a budget, keeps or trims it across turns, and hands it
between agent phases. Each step is a design choice, and each one can lose
information.

Research on agent context mostly asks how big the window is and how the
model attends within it~\cite{liu2024lost}, or how to extend it with
memory~\cite{packer2023memgpt}. Papers about harnesses treat the scaffolding
as a detail~\cite{yang2024sweagent,jimenez2024swebench}. One recent study
reads the source code of eleven production harnesses but measures no
effects~\cite{harness2026}. Failure taxonomies label what went wrong across
thousands of agent runs~\cite{cemri2025mast}. Three concurrent studies land
closer to ours. One asks how well models process a tool's \emph{complete}
JSON output~\cite{kate2026tooloutputs}; we ask whether the output reaching
the model is complete at all. One measures harness-driven outcome variance
across models and tasks~\cite{yao2026harnessbench}; we trace variance to one measurable boundary instead of the
outcome level. One shows that keeping tool output in a file for
retrieval, instead of placing it in context, costs accuracy on some models
and not others~\cite{zhang2026samesimulation}; our mechanism is destructive
delivery, not a retrieval choice. The shared gap is this: a run log records
what a tool \emph{delivered}, not what it \emph{produced}. A loss on the way
into the log cannot be found in the log.

We measured this gap directly, in an agent that finds the root cause of
injected faults from Linux kernel traces. Three facts came out of that
measurement.

First, the window was nearly empty. The largest single prompt across all
$720$ runs was $23$k tokens against a $400$k window, just $5.75\%$.

Second, a third of all tool results were destroyed on the way to the model.
The harness cut long results by slicing the JSON text. JSON keeps its keys
in a fixed order, so the slice does not shorten a result; it deletes the
late keys whole. One list of containers reached the model in $4.7\%$ of
$742$ calls. Its sibling list, in the same payloads, reached it in $99.3\%$.

Third, the damage lined up with the task. A fault process that
\emph{starts} during the trace lands in the early list, which survives. A
container that was \emph{already running} appears only in the late list,
which dies. Accuracy split along exactly that line, on both test
applications: faults that spawn a process scored $40$--$55$ out of $60$,
and faults in already-running containers scored $0$--$24$ out of $60$. We
had read this gap as a limit of kernel traces. The delivery numbers say our
own harness played a part. How large a part is the open question, and we
report both what our experiments settled and what they did not.

Our contributions are: (1) a five-stage pipeline model of agent context,
with a measured failure at each stage (Sec.~\ref{sec:pipeline}); (2) a way
to measure the loss, using per-stage counts and a single \emph{yield}
number, applied to our own harness (Sec.~\ref{sec:ablation}); (3) replay
evidence, including the shipped cut deleting a culprit's whole evidence
class on a production-scale trace (Sec.~\ref{sec:measured}); (4) a
registered, controlled experiment whose result is a \emph{compensation
tax}: where the agent has other routes to the answer, the cut costs work,
not accuracy (Sec.~\ref{sec:ablation}); and (5) a survey of seven agent
frameworks finding this position-based cut in two of them, with no
consistent alternative in the rest (Sec.~\ref{sec:measured}).

\section{Context as a Pipeline}
\label{sec:pipeline}

We model the path from tool output to decision as five boundaries
(Table~\ref{tab:pipeline}). No agent can skip them. Every tool-using agent
must serialize results, cut them to some budget, keep or trim them across
turns, and move conclusions between phases. A harness that seems to skip a
stage has simply picked a default for it. The five boundaries are not one
failure mode: S1 and S4 destroy or strand evidence outright, S2 is a
resource wall rather than a content loss, S3 inflates cost without deleting
anything, and S5 is disabled here by choice rather than observed to fail.
We group them into one pipeline because each is a place where a harness
decides what survives, not because each one loses information the same way.

The loss at a boundary is not random. A cutting rule interacts with the
shape of the data. If results keep a fixed key order and the cut is a
prefix slice, whether a field survives depends on its \emph{position} in
the text. Nothing makes late fields less important than early ones. Models
already attend unevenly by position inside the window~\cite{liu2024lost}.
The harness adds a harsher version of the same problem: a field past the
cut is not attended to less. It is gone before attention ever gets a chance
to see it.

\textbf{Measuring the loss.} We propose to instrument these boundaries and
report, next to accuracy, how much produced evidence survived each one. The
units need to be concrete. At S1 the unit is a top-level field of a tool
result. It counts as delivered when its content is present in the text the
model receives; whether the payload still parses is reported separately.
At S4 the unit is a recorded finding or a captured computation. It counts
as transferred when it reaches the phase that decides. Our summary number,
\emph{yield}, is findings recorded divided by computations run. It is a
narrow, fully measurable proxy for ``work that reached the decision.'' It
does not measure relevance; that needs ground truth, and is future work.

\section{The Defect, Measured}
\label{sec:measured}

\subsection{In the field}
The numbers above come from the harness's deployed evaluation: $720$ runs,
$11{,}189$ tool results, $3{,}827$ cut, all broken, and the
$4.7\%$/$99.3\%$ split over $742$ calls. One thing worth stating plainly:
the accuracy figures came from the strict scorer, which checks a claimed
container against ground truth. They did not come from the lenient scorer
we later caught, and replaced, in our own experiment tooling.

\subsection{Mechanism and replays}
\label{sec:e1}

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{fig_cliff.pdf}
\caption{The delivery cliff. We build a result with the real tool's shape
and replay it through both cutting rules as it grows past the shipped
$6{,}000$-character cap. No model is involved. Under the prefix slice, the
late field arrives whole until the cap, then vanishes entirely and the
payload breaks (bottom strip). The row-aware cut keeps every field at every
size. The stars mark where the real production trace (Sec.~\ref{sec:e1})
falls: $33{,}370$ characters, $128$ records, delivered or lost whole,
exactly as predicted.}
\label{fig:cliff}
\end{figure}

The mechanism is deterministic (Fig.~\ref{fig:cliff}), and it also holds on
real data. Our transcripts store, for every tool call, both the full result
and the exact text sent to the model. We replayed $864$ recorded results
from $31$ runs through both cutting rules. Every result over the budget
broke under the prefix slice, $100\%$ of the time. None broke under
row-dropping. The tools that overflow are the ones that \emph{list things}:
$50\%$ of process-listing calls broke, along with $43\%$ of the agent's own
analysis outputs and $1\%$ of small summaries. Only $2.5\%$ of all calls
were affected at all, which is why a defect like this survives inspection. It is quiet on most calls and fatal on the ones that matter.

We then replayed the shipped cut on a production-scale trace: a real
$21$-container deployment with one service held under a CPU limit. The
culprit here is quiet. It was already running, and it is one Java container
among five, each accounting for close to $1.4\%$ of kernel events. The
listing result is $33{,}370$ characters, $5.6\times$ the shipped budget, so
nothing here is calibrated. The shipped slice delivers $30$ of $118$
early-list records and \textbf{$0$ of $128$} late-list records, in a broken
payload. On the deployed data, at the deployed budget, the culprit's whole
evidence class disappears before the model ever sees it.

\subsection{The same cut in other frameworks}
We read the tool-output cutting code in current releases of seven agent
frameworks (langchain-core 1.6.12, langchain 1.4.6, smolagents 1.26.0,
openai-agents 0.24.0, autogen-agentchat 0.7.5, pyautogen 0.10.0, crewai
0.11.2). Both general-purpose cutters we found slice by position.
langchain-core slices serialized tool output to $500$ characters, keeping
the front. smolagents deletes the \emph{middle} of any observation over
$20$k characters. Neither looks at the structure of what it cuts. Three
frameworks cut nothing, which simply pushes the loss to the window instead.
One cuts only tracing data. The one structure-aware cutter we found, a
shell middleware that cuts by lines and says so, shows that the safe
pattern exists. It is just not the default.

\section{The Controlled Experiment}
\label{sec:ablation}

The field numbers show a match, not a cause, and the original repair
shipped together with new tools, so its effect cannot be separated out. So
we put each defect back on its own, holding everything else fixed. We wrote
down our predictions before each wave of runs, and every change to the plan
is logged, with its date and reason, in a file that ships with the
artifact.

\textbf{Setup.} The subjects are kernel traces of a coding agent running
under resource limits, with exact ground truth. The diagnosing agent, model
(temperature $0$), tools, and task all stay fixed. There are two fault
classes: \emph{spawned}, where the culprit process starts mid-trace, and
\emph{resident}, where it was already running. Healthy traces serve as the
negative controls. Every run gets the same one-line symptom report. The
configurations are \emph{repaired} (row-aware cut, automatic hand-off),
\emph{S1 defect} (prefix slice, at the budget that actually bites on these
traces), \emph{S1 reversed} (the same defect, but the keys are serialized
in reverse order, so the content is unchanged and only the positions move),
an \emph{order-only} control (reversed keys, no cut), single-defect arms
for S2 through S4, and \emph{all defects} together. Each class has $5$
distinct recordings times $3$ repeats, paired across configurations, for
$145$ runs in total; none failed. Scoring counts only a \emph{commitment}:
the agent must name the culprit in its answer field, and we check that name
against ground truth. A mention in passing does not count. Our first
scorer counted mentions instead, which inflated one arm from $2/15$ to
$14/15$. We caught this by auditing at $46$ runs and replaced the scorer.

\textbf{Results} (Table~\ref{tab:compensation}). The window was never the
limit. A run used a median $567$k input tokens in total, spread over a
median $53$ calls, about $10$k per call, which is $2.5\%$ of the $400$k
per-call window at that median. Under the defect, the agent lost a median
$27$ results per run, $40\%$ of its calls, every one broken. It still named
the spawned culprit in $15/15$ runs, against $14/15$ for the repaired
condition. That difference is noise at this sample size; it does not mean
the defect helps. What actually moved was the work. Tool calls went from
$53$ to $68$ to $76$, a rise of $28\%$ and then $43\%$. Computations went
from $18$ to $32$ to $36$, roughly doubling. Input tokens rose $5\%$, then
$14\%$. Yield fell from $0.61$ to $0.34$ to $0.31$. The yield falls because
wasted production grows, not because findings drop; findings stay at $11$
throughout. The order-only control lands back at exactly $0.61$, which
also checks the metric itself. At equal answers, the extra tokens are
unnecessary inference overhead that end-to-end latency will not show.

\textbf{The reversal test, and a refuted prediction.} We registered a
prediction: reversing the key order would move the culprit's list from
fully delivered to fully deleted, so accuracy should drop. The manipulation
worked exactly as planned. The transcripts show the culprit absent from
every listing payload. Yet the agent still named it, $15/15$. It recovered
the name through its own code: the culprit is the loudest process in the
trace, responsible for $14.0\%$ of kernel events, so every sorted table the
agent builds puts it in the first rows, inside the part that survives. The
order-only control stayed flat, so this recovery is real, not an artifact
of the scoring. What replaces our original prediction is a sharper
rule: \textbf{the cut hurts only where the agent has no second route to the
answer, and its cost shows up as extra work before it shows up as
errors.} A loud culprit survives the loss of any single route. A quiet
culprit that lives in one field, like the resident case in the field data,
delivered at just $4.7\%$, has no second route.

\textbf{Two predictions we could not test.} H3 said that removing the S4
hand-off channel would turn failures into confident ``nothing is wrong''
answers. But the repaired baseline already answers ``normal'' on $14$ of
$15$ resident runs, so there is no room left to show a shift. H4 said that
yield predicts accuracy better than window use does. But accuracy barely
varies inside each class, so no predictor comparison is possible here. Both
predictions stay registered and untested. The S4 worry itself is grounded
in the field data: one worker computed the deciding rate, saw it fall from
$1{,}242.8$ per second to $0$, passed the finding on to no one, and the run
still concluded ``normal.''

\textbf{A direct replay, repeated, at production scale.} Three early
attempts to show the cut destroying \emph{accuracy}, not just data, on the
production trace from Sec.~\ref{sec:e1} failed outright: with no working
repaired baseline, there was nothing for the defect to break. We then
fixed two things: delivery itself, so a result is never truncated
mid-record, and the step budget, giving each worker more tool-calling turns
before it has to stop. We also built a page-on-request mechanism around
this time, a safety net for results too large for one page, but it never
fired here: every result already fit on the first page, so it gets no
credit for what follows. We reran the identical
trace and prompt under both conditions, repeated. Repaired: $3$ of $6$ runs
name the throttled service correctly, with $0$ of $6$ broken payloads. S1
defect, same trace, same prompt: $0$ of $5$ correct, and every run shows
broken payloads, $10$ to $14$ each. The data-destruction half is now
exceptionless at production scale, not just in the curated replay corpus.
The accuracy half moves the same direction but is noisier at this sample
size: three of the six repaired runs were still wrong, for reasoning
reasons unconnected to data loss. We read this as a direct, repeated
replication of the mechanism at deployed scale, not as proof that the cut
alone drives the field-wide accuracy split.

\section{Why Nobody Notices}
\label{sec:unnoticed}

Three things hide this class of defect. First, it costs almost no time. In
kernel traces of two production coding agents ($10$ uncapped runs, median
$84\%$, range $80$--$91\%$, network and queueing included), the wall clock
is dominated by waiting on the model. The defect's real costs, to
correctness and to token spend, barely touch the metric most teams actually
watch. Second, capacity looks fine. A window that is barely touched gives
no hint that evidence is being discarded somewhere upstream. Third, the
usual remedy hides the symptom. In this system, handing the agent a written
procedure reached the same verdict as free exploration, at just $35\%$ of
the tokens. Teams that feel context pressure add structure, see an
improvement, and stop looking. It is the right fix for the wrong reason: it
needs less delivered evidence, instead of actually delivering evidence
better.

\section{Threats to Validity}

One harness, one domain, one model. We argue the defect class is general
because the pipeline itself is unavoidable, and because two of the seven
frameworks we surveyed cut the same way, with no consistent alternative in
the rest (Sec.~\ref{sec:measured}). The same shape recurs whenever a
harness truncates a compiler error, a CI log, or a failing test's output
before a coding agent gets to see it. We have not measured other harnesses
end to end, and we have not measured a conventional build-test-fix coding
agent at all; the evidence here is kernel traces only. We also wrote the
defect ourselves, which is why the experiment reintroduces it under
registered predictions rather than telling a repair story. On scale: $5$
recordings per class, with paired repeats, meaning repeats of the same five
recordings rather than five independent fault instances. The experiment's
budget is scaled to its smaller traces, while the production-scale replay
uses the shipped budget unchanged. And as stated above, the accuracy half
of the field split remains correlation, not cause.

\section{Future Plans}

\textbf{(1) The causal accuracy experiment.} Pick a fault family where the
repaired agent is known to succeed and the culprit is quiet, so the
baseline reliably solves it. Hold the trace, fault, prompt, model, and
tools fixed, and vary only delivery: a complete result, a prefix
truncation, a reversed key order, a row-aware truncation, and
paging-on-request recovery, a safety mechanism we have not yet seen fire. For every run, report four checks: whether the culprit's
records are visible to the model, whether the payload is valid or broken,
whether the culprit is recoverable by other tools, and the final answer,
across independent instances, not repeats of a few.
\textbf{(2) A deeper survey.} Extend our reading of seven frameworks across
the eleven-harness corpus of~\cite{harness2026}, classify every cutter as
position-based or structure-based, and run each one against the
delivery-cliff replay. \textbf{(3) Reporting loss as standard practice.}
Package the instrument so any harness can print its loss profile next to
its accuracy number. The claim to test: harnesses with equal accuracy
differ in yield, and yield predicts how they perform on harder tasks.
\textbf{(4) Tests without a model.} Each failure in Table~\ref{tab:pipeline}
is mechanical, so CI can catch it directly: a result that does not survive
its own cut, a step budget with a pile-up at its limit, a phase boundary
that drops computed results. A replication package, with drivers, scorer,
per-run results, the replay corpus, and the registered plan with its dated
amendment log, is prepared for artifact submission.

\section{Conclusion}

An agent's context is not a window it is simply given. It is the output of
a pipeline that its harness built. In a working system, that pipeline
destroyed a third of all tool results while the window sat $93\%$ empty.
It deleted evidence by position, not by value. Where the agent had another
route to the answer, the loss turned into measurable extra work instead of
outright errors. Every harness makes these choices. None of them report
them. They are easy to measure, and we have shown how.
