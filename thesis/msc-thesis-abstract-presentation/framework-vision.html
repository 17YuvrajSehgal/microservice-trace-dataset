How a blueprint works when somebody says “the front-end is slow”

A library of solved investigations is only useful if an agent can pick the right one from a vague complaint and run it unaided. This document walks that path end to end, and marks honestly which parts exist today and which are the proposal. The back half is built. The front half — choosing — is the thesis.

The run-time path

One complaint goes in. One of three honest answers comes out. The library sits above the path rather than inside it, because it supplies two different things at two different moments: candidates when the agent is deciding what this might be, and instructions once it has decided.

The same path, walked for one complaint

The operator says eight words. The agent is told nothing else — not that a fault happened, not when, not which service is at fault. Here is what each stage does with that, and the kind of evidence it would turn up.

This walk is an illustration, not a recorded run. The stages are the designed ones; the numbers in the evidence strips are real discriminators and thresholds taken from our blueprints, arranged to show how the path resolves. No single run produced this exact sequence.

00

Intake — turn a sentence into a question

Eight words carry three facts and one gap. Scope: one service, not the whole host. Symptom class: latency, with no claim of errors. And the gap: slow compared to what, and since when? The output is an issue class, not a cause — that is the entry point to the hierarchy.

scope        one service — front-end
class        latency           (not: errors, not: outage)
missing      a window, and a baseline to compare against
→            enter the LATENCY parent blueprint
01

Triage — is anything actually wrong?

Compare the incident window against the system's own earlier behaviour. If nothing moves beyond a margin, the honest answer is “healthy” and the run stops there. This step does not exist yet, and it is the one that decides whether the framework is usable in production: a tool that finds a fault in a healthy system is worse than no tool.

front-end p95 vs its own baseline      4.1x   → something moved
error rate                             flat   → it is slow, not broken
→ continue
02

Survey — one fixed set of cheap measurements

The same small set for every incident, so it cannot leak the answer. From the kernel trace alone: on-CPU time per container, runqueue delay, blocking-syscall durations, retransmissions, reclaim events, fork rate, disk requests. The output is a set of symptom words drawn from a shared vocabulary.

Why shared matters: if every blueprint invents its own words, matching on them scores almost perfectly — not because selection works, but because the word names the answer. Today 22 of our 24 symptom words are used by exactly one blueprint, so this has to be fixed before any selection number means anything.

host CPU                      raised, with headroom   (not exhausted)
a newcomer container          none
front-end CPU waits ≥50ms     none                    → not a CPU story
front-end → datastore gap     0.9ms → 418.7ms
answers still arriving        yes                     → slow, not down
retransmissions on its flows  0.0%                    → path is clean
03

Narrow — the parent blueprint routes, it does not diagnose

LATENCY asks one question: where is the time going? Waiting for a CPU, waiting on something else, lost in the path, or stalled on memory. The survey already answers it — CPU waits are absent and a connection gap jumped — so the whole CPU branch is eliminated without running anything expensive.

LATENCY
├─ waiting for a CPU        ruled out — no long CPU waits anywhere
├─ waiting on a dependency  candidate — the gap jumped 465x
├─ degraded network path    weak      — retransmission is 0.0%
└─ against a memory limit   ruled out — no memcg reclaim events
04

Rank — score the candidates, drop most of them

Symptom words that match score up. A do_not_apply_when condition that is true scores down hard. A failed cheap_precheck drops the blueprint entirely, before any expensive work runs. The output is an ordered shortlist, not a single pick — the order is what gets scored.

1.  db-latency-dependency-wait    strong   gap jumped, answers flowing
2.  network-path-degradation      weak     kept as a fallback
    service-cpu-throttle          dropped  precheck: no CPU waits
    cpu-contention-co-tenant      dropped  precheck: no newcomer
    service-memory-cap            dropped  precheck: no reclaim
    … 16 others                   dropped
05

Collect — the blueprint says what it needs

This is the half that makes a blueprint more than an analysis script. The chosen blueprint declares its collection_order: exact tracepoint names and a window split into baseline, incident and recovery. If the evidence is already on disk, nothing new is recorded. If it is not, collection escalates cheapest-adequate-first — existing evidence, then low-overhead sampling, and only then full tracing.

An overhead policy gates the escalation: querying what exists is automatic, while active collection above a budget needs a human to approve it.

needs      syscall entry/exit on the front-end's sockets
           sched_switch, sched_waking   (as the negative control)
window     60s baseline · 120s incident · 60s recovery
tier       existing evidence is sufficient — collect nothing new
06

Execute — capability, then a real command

Every step names a capability, never a tool. A registry binds that to whatever is installed here. Steps run in order, each with an expected result so a failure is detectable rather than silent. A step the data cannot reach is marked, skipped, and its absence is not treated as evidence.

Note the first step. It is a gate, added because the agent once called a CPU-starved machine a dependency problem: everything talking to a starved process shows inflated gaps, so gaps on a starved machine mislead.

step 1  CPU GATE — any long CPU waits anywhere?   none → continue
step 2  request-to-answer gap per socket        10 fds at 0.46–0.56s
step 3  is it a pool?                           yes — 6 fds, same numbers
step 4  slow, or no answers at all?             answers arriving → slow
step 5  who is the peer?                        mirror rule → mysqld
step 6  is the peer itself struggling?          no CPU, no disk strain
07

Decide — and be willing not to

Every verdict_when condition must hold. If a rule_out condition is true instead, the blueprint stops and names the blueprint to go to — control returns to selection rather than forcing an answer. Below the confidence floor it collects more, up to a round limit, then hands back.

verdict      db_latency — the app-to-mysqld connection path
where        the front-end's connection pool; peer observed as mysqld
evidence     gap 0.9ms → 418.7ms; peer mirrors it at 0.3 → 501.6ms
reasoning    no CPU or disk strain on mysqld → the PATH, not the database
confidence   0.92
—

The branch that matters just as much

Had the CPU gate in step 1 found long waits, the blueprint would have stopped there and handed the case to the CPU-cap blueprint. Had the pool check found a single slow socket among many fast ones, it would have reported that its signature did not apply here rather than naming the next most suspicious container.

We have measured both halves of this. On an application whose callers already pool connections, the connection-pool blueprint's signature reads 0.7–1.1 setup calls/s against 169–177 where it works — so it declines. And in a cross-fault test, one blueprint correctly refused a dependency diagnosis on a CPU-cap run after the gate fired.

08

Feed back — into collection, and into the library

Two loops, and they are what separate this from a pipeline that runs once.

Into collection: the verdict names the signal that decided it, so next time that signal is recorded by default and the cheaper tier is enough more often.

Into the library: a wrong or hedged answer becomes a blueprint revision, not a lost run. That loop is measured — it took one blueprint from a confident wrong answer to three correct cells out of three, and a second from 2 of 4 to 4 of 4.

Inside selection: why this is not “try all of them”

The obvious way to use a library is to run every blueprint and keep the best answer. That is also the baseline a reviewer will reach for, so the framework has to beat it on cost while matching it on accuracy. Cheap prechecks are how.

The hierarchy, and where the library stops

A flat library makes the agent guess from a long list. A parent blueprint per issue class makes it narrow instead. The parent carries no diagnosis of its own — its only job is to eliminate branches cheaply and hand off.

How the library gets to twenty-one, and then to more

Blueprints are not written from knowledge. They are written from measurement, in a fixed order, and the order is never reversed. A blueprint that fails its agent test is revised rather than discarded — which means the agent's mistakes are an input to the library, not just a score.

Why selection is the honest focus. In a 57-incident study the library scored level with no library at all on the faults it covers — 56% against 56%. Underneath that tie, blueprints fixed 3 runs and broke 4, and all four breakages were the wrong blueprint being selected. Not one was a blueprint giving bad advice about its own fault. The network blueprint was picked zero times across nine network incidents, while the deterministic engine scores 9 of 12 on those same faults using that same blueprint.

So the content is not the bottleneck. The routing is — which is why Select is the only stage in teal, and why the proposed work starts there.

The library is the contribution. Any single blueprint is just an entry in it.
