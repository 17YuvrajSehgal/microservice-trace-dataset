Software is now diagnosed by AI agents. This thesis is about making that diagnosis something that accumulates instead of being redone every time.

02 Background

Diagnosis starts with telemetry

A running system emits four kinds of signal. When something breaks, an engineer reads them and works out why.

Metrics Numbers sampled over time — CPU use, request latency, error rate.
Logs Lines the code chose to write down.
Traces One request's path across services, with timings per hop.

where every public incident dataset stops

Kernel traces Every system call, every scheduler decision, every packet — collected below the application. No service names, no request ids.

The first three describe what the application says about itself. The fourth records what the machine actually did.

03 Problem 1

We keep the fix. We throw away the method.

Diagnosis is skilled work. It means knowing which signal separates one cause from another, which events are worth recording at all, and which threshold means something on this system rather than in general.

What a closed ticket keeps

The fix. A one-line resolution. Sometimes a dashboard screenshot.

What it loses

The signal that actually separated the causes. The events someone decided to collect. The threshold that meant something here. The three things that were tried and did not work.

A tool team solves hard kernel-level problems — each one potentially a paper. But there is no history. "The history is in Mohammed's brain."

So the next investigation starts from nothing — whether the next investigator is a new engineer or an AI agent. And a language model has no particular idea what a CPU cap looks like in a scheduler trace.

05 The idea

An observability blueprint

One solved investigation, written down so it can be re-executed — by a person or by an agent. It records what to collect, what to run, and how to decide — not just what was concluded.

01 Applies-when

And when not to apply it, plus the cheapest check to run first.

02 Collection order

The exact tracepoint names. "Kernel data" is rejected. A blueprint drives collection, it does not only consume it.

03 Runnable steps

Each step is a command with an expected result, so failure is detectable.

04 Decision rule

Measured thresholds, and the look-alike each one rules out.

05 Rule-outs

Mandatory. It must name the blueprint to go to instead.

06 Retractions

What was disproven, kept in the file with the measurement that killed it.

06 The idea · one real example

What "evidence-bound" actually buys you

One discriminator, quoted from the co-tenant CPU contention blueprint. This is the signal any engineer would reach for first.

signal: runqueue delay — sched_waking to the sched_switch that actually runs the thread this problem: raised — measured 7.12x — but this is CORROBORATION, not evidence. It must never be the deciding signal. NOT this: runqueue delay alone separates nothing. It is raised in every CPU-family fault, and in healthy load bursts too, and its ordering is INVERTED against severity.

Runqueue delay, measuredvs its own baseline
Host CPU exhaustion52×

 Ordered by how loud the signal is, the actual target comes third — behind a fault it is meant to be distinguished from, and barely ahead of a healthy box.

The obvious signal was measured, and demoted to corroboration. No prose runbook does that.

07 The idea · two properties

Why this is not a runbook

It is executable

A step declares a capability, never a tool:

needs: kernel.scheduler.runqueue_delay

A registry binds that to whatever is available — our Babeltrace2 script here, Trace Compass or a vendor's own analyser elsewhere. Swap the tool and the blueprint does not change. 22 capabilities registered.

It is evidence-bound

No claim enters a blueprint until it is measured on our own data — and measured against every fault family, not only its own. A validator rejects uncited claims.

33 thresholds live in one file, each recording whether it transfers to another machine. A threshold in cores measures our hardware; a ratio to the run's own baseline measures the fault.

The rule cost us our first three favourite ideas

Our first draft claimedWhat 93 labelled runs showed
the delayed services show raised runnable-wait never exceeds 4% in any fault family — and was 1.6% on the co-tenant case itself. Unusable.
the culprit's wait breakdown identifies it host-attributed faults have no culprit-side record at all. Five whole families. Unmeasurable.
the suspect shows dominant off-CPU I/O wait true — and equally true of every family, 98–99%. Identifies nothing.
 All three would have been on a slide. Retracted claims stay in the blueprint, with the measurement that killed them, so the agent is warned off them too.

What this turns trace analysis into

Not a stateless pipeline that runs once, but something that gets better as it is used. A new blueprint makes the next incident cheaper, and a corrected one makes every future run more accurate.

What runs automatically today — honestly

The blueprints and the rule engine run. Selection is manual. The knowledge objects are built and proven; the machine that routes between them is the next phase, and slide 13 is why.

10 What exists · library and agent

A library, and an agent that cannot cheat

The library

16 blueprints, 11 wired into the experiment harness. 33 measured thresholds, 22 capabilities.

A second generation of 5 is being built by the loop on slide 14 — 24 agent-verdict cells so far, and zero confident wrong answers.

The agent

Plan → parallel workers → review → synthesise. Seven read-only tools over the raw kernel trace, plus a sandboxed Python interpreter so it is not limited to questions our fixed tools can express.

The controls

Ground truth is unreachable by construction — it sits in the run directory, so the sandbox is never given a path, only a pre-loaded table. Names are masked, skills are leak-scanned, every transcript is audited. 19 adversarial escape attempts check the sandbox.

The agent is never told that a fault happened — let alone when.

Phase one uses kernel traces alone: no service names, no request ids, no log lines. The hardest case, and the least studied. If a blueprint helps there, it is carrying real method rather than restating a log line.

12 Early evidence · executable beats prose

Rules transfer. The same rules as prose do not.

A deterministic rule engine built from the same blueprints. Same kernel data. No model at all. 81 test runs, two applications.

38/41right when it fires — 93% precision
26/29correct silences on runs it should ignore
5/5healthy runs correctly declined
64/81correct overall (79%)

The same knowledge, written as markdown and handed to a capable model, gets roughly half that.

And a clean negative control, from a separate 12-incident study

Giving the model the kernel evidence pack changed nothing: it named the same component on 12 of 12 incidents, for +61% more tokens. More data, handed over as text, bought zero accuracy. The deterministic blueprint scored 83% fully correct on those incidents against 58% for every model arm — and 5/5 on the co-tenant fault that no model arm ever got right.

This is why the abstract says executable — and it is one of the four evaluation questions, not a side observation.

What moved underneath the tie is the useful part

  • Blueprints fixed 3 runs. Two were co-tenant CPU contention — a fault the unaided model got right 0 times out of 6.
  • Blueprints broke 4 runs. All four were the wrong blueprint being selected. Not one was a blueprint being wrong about its own fault.
  • The right blueprint was picked 19 times out of 27.
  • The network blueprint was picked zero times across 9 network incidents — while the rule engine scores 9/12 on those same faults, using that same blueprint.

The content is not the bottleneck. The routing is.

14 Early evidence · the method working

The loop that builds a blueprint is itself the result

Every blueprint is tested by the agent on its own fault, plus a healthy negative, plus a different fault, plus the reverse — another blueprint on this one's fault. The negatives and cross-cells are the point.

blueprint → agent run → failure analysis → targeted fix → correct verdict

BlueprintVerdict cellsWhat the loop found
Service CPU cap0/1 → 3/3 "The blueprint assumes a cap hits one process; a cgroup cap hits a process tree."
Co-tenant contention3/4 → 4/4 Fair sharing mimics a quota ceiling. The separator is the idle share — 96% against 1%.
Slow dependency2/4 → 4/4 Blocking-read duration measures nothing on an async runtime: every read took 0.0 ms while every request took 500 ms.
Service memory cap5/5 First try, no iterations — the earlier lessons carried over.
Service network4/4 Tested on unseen data from day one. 0.94 confidence on a run it had never seen.
 Across all of it: zero confident wrong answers. The repeating pattern — negatives clean, positives find the right evidence but under-commit, cross-cells expose exactly one missing rule.

And on unseen data from the real dataset, each blueprint solved the other's fault by routing to it — while being honestly cautious about its own. That is the library behaving like a library.

15 Early evidence · abstention

A blueprint must be able to say "not applicable here"

Two faults proven not diagnosable from kernel traces

A frozen service, and a silent queue backlog — after six and one measured attempts. Both are defined by absence: the container stops answering without losing packets or going quiet in the scheduler.

This matches what our pre-registered fault catalogue predicted before collection began.

Screening anti-patterns from real faults

Wrong fires 29% → 12%, with zero correct diagnoses lost. 27 false diagnoses removed.

And a measured example of refusal: connection-pool exhaustion on an application whose callers already pool connections — 0.7–1.1 setup calls/s against 169–177 where it works. The blueprint reports that the check did not apply, rather than naming the next most suspicious container.

A blueprint that always produces an answer is not carrying knowledge. It is guessing with structure.

Four questions, each already designed

QuestionDesignStatus
Does a blueprint transfer to another service and another system? Author on one run; test on another service, another intensity, another application. partially measured
Does the library abstain when nothing fits? Leave-one-family-out, with healthy runs as negative controls. measured
Do executable steps beat prose describing the same step? Code in the blueprint versus the identical step as text. strong early signal
Can the right blueprint be selected from evidence alone? Hierarchical routing — issue class to cause — against a flat library. the measured bottleneck

Controls that stay in place

deterministic brief in both arms leakage lint healthy runs as negatives repeats, so the noise floor is designed in

The control is deliberately unkind. We measured that a one-shot model call with a good deterministic brief already ties a full tool-using agent, at 27% of the tokens. A blueprint has to earn its place against that.

18 Proposed work

Six phases

PHASE 1Latency taxonomyEnumerate the causes; state which kernel traces can observe.
PHASE 2Hierarchical selectionThe measured bottleneck. Narrow instead of guessing from a flat list.
PHASE 3Micro-benchmarksOne cause each, traced repeatedly. Removes the two-app objection.
PHASE 4The harder experimentNeither arm gets pre-computed evidence — tests the collection half.
PHASE 5TransferAnother service, another app, then a dataset that is not ours.
PHASE 6WritingA technical report per problem, then the thesis.

Phase 4 matters more than it looks. Every experiment so far handed both arms the evidence pack — so we have tested how to read the numbers, and never yet tested what to collect. That is the half a blueprint should be best at, and the half a model has no way to guess.

A2 Backup · for questions

When a blueprint makes an agent worse

600 runs, two applications. On a network fault the blueprint arm found the incident window far less often than the arm given nothing. It did not answer wrongly — it answered unknown.

Abstained on the windowWithout blueprintWith blueprint
Sock Shop, out of 30114
Train Ticket, out of 30923
 Both applications, same direction, same size.

The deciding check was a threshold on a rate. The agent can show retransmission is or is not happening, but the deployed tools cannot compute a percentage. So it saw the signal, could not satisfy the check as written, and honestly declined.

A blueprint whose deciding check is a threshold on a quantity the deployed tools cannot compute will make an agent abstain — even when the underlying signal is plainly visible.

Now part of the method: every thresholded discriminator needs a qualitative fallback, and a blueprint must state which of its checks are unreachable in the current deployment. This is a portability result, and it is why "executable" has to mean executable here.

A3 Backup · for questions

How a run is scored

One accuracy number is not enough, because "right answer" has several independent parts. A run can get one right and the others wrong.

WHERE

A kernel trace has no service names, only a numeric namespace id. Naming a container is verified against the true id, never taken on trust.

WHEN

Overlap with the true injection window. unknown is an honest abstention — scored as nothing, not as wrong.

Earliness

How early it noticed, gated by overlap — because earliness alone is trivially gamed by claiming the whole recording.

WHAT

Concept coverage of the agent's own prose, not a label match. An agent that describes the fault correctly in its own words should not score zero.

And harness health prints above the result, deliberately

Three times we read a low score as a limit of kernel traces, and all three times it was our own plumbing. The worst: a reply cap sliced tool results mid-JSON, so the field identifying an already-running container reached the model 4.7% of the time while the field identifying a spawned one reached it 99.3%. The scores split exactly along that line — and peak context use was 6.6%. We were destroying evidence to save room nothing was using.

Check the harness before believing the score.
